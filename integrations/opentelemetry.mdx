---
title: "Use existing OpenTelemetry"
description: "Send standard OTLP traces and correlated logs to Hue without changing how your application calls models."
---

If your application already emits OpenTelemetry, send those records to Hue through an OTLP HTTP exporter or collector. You do not need a Hue-specific model wrapper.

## Configure the destination

Use a **Tracing only** project service key from **Settings → Integrations & API keys**. The key determines the destination project; a project ID inside an attribute does not grant access. Use **Read and write** only when this process also calls evaluation APIs.

| Setting | Value |
| --- | --- |
| Trace endpoint | `https://app.hue.run/api/v1/otlp/v1/traces` |
| Log endpoint | `https://app.hue.run/api/v1/otlp/v1/logs` |
| Transport | OTLP over HTTP, protobuf or standard OTLP JSON |
| Authorization header | `Authorization: Bearer ` followed by your project service key |
| Optional compression | gzip |

Set the complete signal-specific endpoints in your exporter's configuration. Do not accidentally append another `/v1/traces` or `/v1/logs` to them. Store the authorization value in your server environment or secret manager.

These routes accept the OpenTelemetry wire format, not arbitrary application JSON. Metrics ingestion and OTLP gRPC are not currently supported. Logs support trace-correlated evidence; this is not a general log-search service.

## Attach Hue transport to JavaScript providers

If you want Hue's content controls and export diagnostics while keeping provider ownership, attach its processors when you construct your providers. [Install the TypeScript package](/installation#typescript), then install these explicit provider dependencies:

```sh
bun add @opentelemetry/sdk-trace@2.11.0 @opentelemetry/sdk-logs@0.222.0 @opentelemetry/resources@2.11.0
```

Save the following as `otel.ts`. This standalone example owns the providers it creates. In an existing application, add the processors to your existing provider construction and retain your normal global registration and propagation setup.

```ts
import { createHue, createHueTransport } from "@hue-run/sdk";
import { TracerProvider } from "@opentelemetry/sdk-trace";
import { LoggerProvider } from "@opentelemetry/sdk-logs";
import { resourceFromAttributes } from "@opentelemetry/resources";

const apiKey = process.env.HUE_API_KEY;
if (!apiKey) throw new Error("Set HUE_API_KEY in your server environment.");

const transport = createHueTransport({
  apiKey,
  serviceName: "existing-otel-demo",
  captureContent: true, // Keep recorded prompts, responses and tool inputs/outputs.
});
const resource = resourceFromAttributes({ "service.name": "existing-otel-demo" });
// Add Hue processors when constructing your application's providers.
const tracerProvider = new TracerProvider({
  resource,
  spanProcessors: [transport.spanProcessor],
});
const loggerProvider = new LoggerProvider({
  resource,
  processors: [transport.logRecordProcessor],
});
// Reuse these providers for Hue helpers and your existing instrumentation.
const hue = createHue({ transport, tracerProvider, loggerProvider });

try {
  await hue.checkConnection();
  const span = tracerProvider.getTracer("example.instrumentation").startSpan("example.work");
  try {
    span.setAttribute("example.operation", "verification");
    console.log("Trace ID:", span.spanContext().traceId);
  } finally {
    span.end();
  }
  // Export after the span ends, then inspect the delivery counters.
  console.log("Delivery counters:", await hue.flush());
} finally {
  try {
    await hue.shutdown();
  } finally {
    await Promise.allSettled([tracerProvider.shutdown(), loggerProvider.shutdown()]);
    await transport.shutdown();
  }
}
```

Run `node otel.ts` after setting your environment. An export rejection makes the command fail rather than reporting successful delivery. Hue does not register or replace a global tracer, logger, or context manager. An instrumentor that only uses global providers still needs your application's normal OpenTelemetry initialization.

Your providers own the resource in this mode: set `service.name`, `deployment.environment.name` and similar attributes on them. `resourceAttributes` on the transport options is ignored and reported as a `warning` issue. The Python SDK attaches the same way through `tracer_provider=` and `logger_provider=`; a provider Hue creates for the other signal reuses the borrowed provider's resource. See the [Python guide](/sdks/python#use-an-existing-provider).

## Keep Langfuse and add Hue

If Langfuse already receives your application's spans, keep its instrumentation and exporter. Add Hue's span processor to the **same provider at construction time**. Find the module that creates your existing `NodeSDK`, `NodeTracerProvider` or framework-owned provider; do not create or register a second global provider. Preserve its resources, sampling, context propagation, existing processors and Langfuse filters. See [Langfuse's existing OpenTelemetry guidance](https://langfuse.com/faq/all/existing-otel-setup).

For example, this is the change to an existing `NodeSDK` setup after installing `@hue-run/sdk`; keep the rest of that application's initialization:

```diff
+ import { createHueTransport } from "@hue-run/sdk";

  const langfuseSpanProcessor = new LangfuseSpanProcessor();
+ let hueTransport: ReturnType<typeof createHueTransport> | undefined;
+ try {
+   hueTransport = createHueTransport({
+     apiKey: process.env.HUE_API_KEY ?? "",
+     enabled: process.env.HUE_TRACING_ENABLED !== "false",
+     serviceName: "my-agent",
+     captureContent: true, // Authorize capture and configure redaction for Hue too.
+   });
+ } catch {
+   // Keep existing tracing available. Do not log the key or exception object.
+   try { console.warn("Hue tracing initialization failed"); } catch {}
+ }

  const sdk = new NodeSDK({
    spanProcessors: [
      langfuseSpanProcessor,
+     ...(hueTransport ? [hueTransport.spanProcessor] : []),
    ],
  });
```

This illustrates the attachment point, not a replacement bootstrap or a compatibility certification for your installed versions. In a serving application, construct the optional Hue transport inside your existing fail-open initialization boundary and append its processor only when initialization succeeds; the rest of tracing must still start. The [production-safety guide](/guides/production-safety) explains bounded cleanup and failure isolation. If a framework owns the provider, use its supported processor configuration instead of starting another provider.

Keep the AI SDK instrumentation that already feeds Langfuse: AI SDK 6 uses `experimental_telemetry`, while AI SDK 7 uses its registered telemetry integration. Do not replace that integration with a per-call `hueTelemetry()` helper: a per-call integration list replaces the global list for that call. Follow [Langfuse's version-specific AI SDK setup](https://langfuse.com/integrations/frameworks/vercel-ai-sdk) and [Hue's tested compatibility](/sdks/compatibility).

Langfuse's `mask` hook belongs to its export path. Do not assume it redacts the copy sent through Hue's processor. Apply the same approved policy before both exporters or configure each exporter's redaction separately, and inspect both outputs using synthetic content. See [Langfuse masking](https://langfuse.com/docs/observability/features/masking) and [Hue capture policy](/guides/production-safety#capture-titles-and-retention).

Hue reads Langfuse's span attributes as they are, with no Langfuse-specific setup. `langfuse.observation.type`, `langfuse.observation.model.name`, `langfuse.observation.usage_details` (input and output tokens), `langfuse.observation.input` and `langfuse.observation.output`, `langfuse.session.id` and `langfuse.user.id` fill Hue's operation, model, usage, content, session and user fields when no OpenTelemetry GenAI attribute supplies them; a GenAI attribute always wins. `langfuse.trace.name` names a trace that has no readable request text. Langfuse metadata, release, environment, tags and levels stay raw attributes, and a Langfuse `level` of `ERROR` does not mark a span failed: Hue reads the OpenTelemetry span status. The [field glossary](/agents/investigate-production#field-glossary) lists every attribute Hue reads.

Hue SDK 0.10.0's metadata-only filter recognizes its [documented content fields](/reference/typescript#content-policy), not every custom attribute. In particular, `captureContent: false` alone does not remove native `langfuse.observation.input` or `langfuse.observation.output` attributes. Omit or redact those fields before they reach Hue, using a producer/collector policy or the Hue transport's `redact` hook. Apply the same rule to custom evidence attributes. Verify the exported result before relying on metadata-only capture.

Verify one controlled request through the application's real entry point. Include a model span and tool span, preserve their OpenTelemetry IDs, finish the stream and flush both exporters within the host's allowed lifetime. Confirm those same IDs, parent relationships, content policy and expected fields in both destinations. Hue's [trace receipt](/sdks/typescript#verify-stored-trace-evidence) proves requested span and field presence; it does not certify payload correctness or Langfuse delivery. A Hue connection check alone proves neither. Repeat for a controlled error and cancellation before enabling ordinary traffic.

A second exporter can only send what the existing instrumentation records. A Python tool's final stdout cannot recover an original response that the application truncated earlier. If later analysis needs original and retained results, instrument that reduction boundary explicitly within your content policy.

## Flush streamed responses in Next.js

For an existing AI SDK 7 app, add Hue's processors to your existing OpenTelemetry providers at startup and retain a `hue` client around that transport and those providers. Keep these instances for the server's lifetime, including your existing exporters and normal provider registration.

The standalone diagnostic above intentionally fails on setup errors. In a serving application, guard the optional Hue setup and use [production-safe initialization](/guides/production-safety). `createHueSafe({ transport, tracerProvider, loggerProvider })` cannot catch an error from an earlier `createHueTransport(...)` call; transport construction must also be inside that optional setup boundary.

In the route, import `consumeStream` from `ai` and `after` from `next/server`, and import the server-lifetime `hue` client from your telemetry module. Replace a standalone `after(flushTelemetry)` with this option inside your existing `createAgentUIStreamResponse` call:

```ts
consumeSseStream: ({ stream }) => {
  // Start reading immediately so generation can finish after the response returns.
  const consumed = consumeStream({ stream });
  after(async () => {
    try {
      // Wait for stream completion before exporting the final spans.
      await consumed;
    } finally {
      const delivery = await hue.flushSafe({ timeoutMillis: 1000 });
      if (!delivery.ok) {
        // Diagnostics must also be unable to break application cleanup.
        try {
          console.warn("Hue telemetry flush incomplete", {
            timedOut: delivery.timedOut,
            ...delivery.report,
          });
        } catch {}
      }
    }
  });
},
```

The independent reader starts immediately and lets the AI SDK finish its completion or abort callbacks before exporting. Keep `request.signal` on generation, but do not pass it to this reader. Your agent and message-handling callbacks stay as they are.

`hue.flushSafe()` flushes the borrowed providers and Hue transport, returns delivery counters without rejecting, and bounds the caller's wait to one second here. A timeout does not cancel a third-party provider's pending work. The raw `transport.flush()` remains a strict diagnostic API and has no `flushSafe()` method.

The example logs only delivery counters. Use an independent, non-throwing monitoring sink for production diagnostics, with rate limiting appropriate to your traffic. Do not shut down a shared transport after each request. Hosting timeouts and process termination can still interrupt delivery. See the [AI SDK stream-abort guide](https://ai-sdk.dev/docs/troubleshooting/stream-abort-handling).

## Map agent data without inventing it

Hue preserves original resource, scope, status, events, links, dropped counts, typed attributes, and external trace/span IDs. It derives AI fields alongside those records using versioned normalization profiles.

Supported profile families include generic OpenTelemetry, GenAI conventions, OpenInference, OpenLLMetry, Vercel AI SDK 6/7, and Langfuse. A profile family is not a guarantee that every package version or API surface has been tested. The TypeScript adapter is verified with AI SDK / OTel pairs `7.0.99 / 1.0.99` and `7.0.100 / 1.0.100`.

Prefer current GenAI attributes when your instrumentation supports them, including `gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.usage.input_tokens`, and `gen_ai.usage.output_tokens`. Preserve unavailable fields as absent. Do not submit `0` for unknown usage or `null` for an output that was never captured.

A child can arrive before its parent, and a correlated log can arrive before its span. Preserve the same trace ID and the correct parent/span IDs across services. Root-span completion does not prove that the whole distributed trace has arrived. Evaluations use a pinned evidence revision.

## Make traces useful to a coding agent

A coding agent that reads your traces over the [Hue MCP server](/agents/investigate-production) can only filter and group by what the spans record. These attributes make its answers precise:

- **Mark failures on the span status.** Hue treats a span as failed only when its OpenTelemetry status is `ERROR`, and a trace is `error` when any finished span is. An `error.type` attribute or a Langfuse `level` alone does not mark a failure.
- **Record a stable user id on every span, sub-agents included.** Use `user.id` (Hue also reads `enduser.id` and `langfuse.user.id`) with the same value everywhere; an id with a suffix such as a tool-call id no longer matches the user's other traces. With Langfuse, `propagateAttributes({ userId }, …)` in TypeScript or `propagate_attributes(user_id=…)` in Python stamps it on every nested observation. A sub-agent that runs in its own trace needs it set there too.
- **Record the session.** Set `session.id` or `gen_ai.conversation.id` on the root span so an agent can list a conversation's traces with `list_sessions` and `search_traces`.
- **Name root spans by task type.** `search_traces` matches its `query` against the root span name, so a stable, descriptive name per kind of work, such as `agent.support_reply`, lets an agent count and time each kind without opening traces.
- **Trace tools as tool spans.** Set `gen_ai.tool.name`, and with content capture `gen_ai.tool.call.arguments` and `gen_ai.tool.call.result`, so failing tools can be counted by name and their inputs and outputs read.
- **Connect sub-agent traces to their parent.** Keep a sub-agent in its parent's trace by propagating the OpenTelemetry context, or, when it must start its own root, add a span link to the handoff span in the parent trace. Otherwise the only connection is an id inside recorded content.
- **Record the release.** Set `service.version` on the resource. Hue keeps it with the telemetry, but the MCP server does not return or filter by it, so also note deploy times to compare releases.
- **Keep development traffic out of production.** Send development and staging traces to a separate Hue project with its own **Tracing only** key, so searches, attention states and intents cover production only.

## Control content at its source

Hue can only show and evaluate what a trace records, so enable your instrumentation's capture of prompts, responses and tool inputs and outputs unless you'd rather not send that content or an application or data policy forbids sending it to another service. When using an external exporter directly, configure capture and redaction in your instrumentation or collector. Hue stores the content it receives; it does not reconstruct missing prompts or apply an automatic retention timer.

Both Hue SDKs strip recognized content attributes from every record on their export path when `captureContent` / `capture_content` is false, including records from third-party instrumentors on a borrowed provider; unrecognized custom keys pass through, so keep the instrumentor's own capture controls configured. Avoid sensitive values in custom metadata regardless of your chosen SDK.

## Observe collector acknowledgements

The request limit is 1 MiB on the wire and after decompression. An individual OTLP value is limited to 256 KiB, and a trace can contain at most 2,000 distinct spans. Oversized requests return HTTP 413.

An otherwise valid batch can receive an OTLP partial-success response containing rejected-record counts. Configure your exporter monitoring to inspect that response; HTTP 200 alone does not prove that every record was accepted. Hue SDKs surface those failures through their flush APIs. Partial rejection must not trigger a blind replay of the whole batch.

Exact completed-span replays are deduplicated within the project. A different payload for the same completed span ID is rejected. Logs have no universal event ID, so exact duplicate records collapse; include their actual timestamps and correlation data. These rules do not make the client's in-memory queue durable.

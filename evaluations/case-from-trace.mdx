A published case contains a task and pinned evaluators, built from one recorded trace. A query and model answer can become an answer-only case without an app simulation or a starting world. A trace with app calls can also pin a world; your agent then runs against a fresh copy with [`hue eval`](/evaluations/eval-ready-agent). For what a world is, see [simulations](/evaluations/simulations).

Mark whether the recorded run was correct and choose an eval set. Hue builds the case and publishes it when verification passes, without a separate review or sign-off. If a check fails, the draft stays available with a correction or retry action. [Manual publication](#manual-publication) remains available for authoring and review.

## Traces that can become cases

Record the task and final answer with full content:

- The current SDK captures content by default; `captureContent: true` in TypeScript or `capture_content=True` in Python also makes the choice explicit. A trace exported without content cannot become a case (`content_not_recorded`).
- Record the task and reply on the task-bearing agent span. A trace with no tool calls can become an answer-only case. **Answer-graded cases from plain traces** is on by default in project settings; an owner or admin can turn it off.
- For a trace with app calls, keep tool names, arguments, results and app identity. Pass the MCP server identity on tool spans (`mcp:` on `hue.tool`) so the trace names the app each call reached. A server version number alone does not identify the app. The case builds a world from supported app simulations or recorded tools; a call Hue cannot read or serve may prevent publication.

Case creation also refuses a trace that is still running (`running`; retry after it ends), selected evidence over 8 MiB, and a trace not recorded by Hue's SDK (`not_hue_sdk`) unless the project accepts generic sources. Direct OTLP traces, including supported Pydantic AI message and tool records, can qualify when their recorded content can be read. Metadata-only capture does not provide the task and answer a case needs.

An empty HTTP or workflow wrapper can contain the task. Hue selects its single task-bearing agent; multiple peer agents require an explicit selection with MCP `root_span_id` or REST `rootSpanId`. Missing, ambiguous or unreadable evidence leaves a reason to correct. Hue cannot reconstruct content that was never captured.

## Answer-only cases

A support reply, summary or other model answer needs no simulated app when the selected turn made no tool calls. Hue pins the trace evidence, keeps the task and allowed earlier context, and generates checks for the answer. The draft has no starting world, app mirrors or replayed calls.

Mark a correct run **Yes** and optionally say why it is correct; that reason supplies required outcome constraints. Mark it **No** and describe what should have happened to generate checks from that intent. Either marking accepts up to 4,000 characters of feedback. Supply the full reason or correction within that limit. An unmarked request waits until it has usable outcome evidence. The original answer is evaluator evidence, not a guaranteed correct answer, and is not given to the agent as part of the task.

Publication pins **Answer outcome** and the required **Answers the task** judge. A rerun must pass the required answer checks and judge to pass the case. A failed required check, including an empty answer, fails the case. Otherwise, a pending, unavailable or undecided required judge makes the result **Inconclusive**. A paraphrase can pass without matching the source answer word for word.

An answer-only case publishes at **T4**. Run it with the [agent command or a connected worker](/evaluations/eval-ready-agent#run-it); the agent receives the task and returns its answer without world setup. Cases that made tool calls use the app or recorded-tool path. A turn without a recorded answer cannot become an answer-only case; a turn that produced output files also needs a supported way to evaluate those files.

## In the Hue UI

1. Open **Traces** and open the trace.
2. Choose **Create case** and answer the one question: "Did the agent complete the task correctly?"
3. Choose the **Eval set** and **Build case**. Hue prepares the task and generated criteria. For app calls, it also builds the starting world.
4. A verified build enters the selected eval set automatically. Open **View case** to inspect the task, evaluators, tier and limitations, or use its run command.
5. If the build stops, open the case and follow its correction or retry action. Correct the task or criteria, add a missing fact, or retry a failed step as appropriate.

Publication saves a version for a new eval set or a draft version Hue opened. When the destination already has an open draft, the case joins that draft; choose **Save eval-set version** before running it.

## What verification establishes

Automatic publication requires outcome checks and technical verification. Newly generated semantic judges are required, pinned and score the new execution. Deterministic checks still verify objective values, the target record, requested writes and procedural constraints, and protect unrelated fields. Historical advisory judge pins keep their policy; answer-only cases retain their required **Answers the task** judge. Manual publication keeps its reviewed answer-case path.

During the build, Hue scores reference runs and negative controls against deterministic outcome checks. Answer-only builds also use answer checks and the required **Answers the task** judge. When an accepted reference is available, Hue checks newly generated required case rubrics against the accepted original for **Yes**, or a successfully replayed corrected run for **No**. A rubric that contradicts that reference enters automatic repair; unavailable or undecided judging keeps its operational failure and retry handling. Checks that accept empty answers, omit requested values or accept known wrong outcomes need correction. If these build checks accept a recorded run marked wrong, the build stops rather than publishing it. Generated semantic judges also grade new executions.

For a world case, replay verifies recorded observations under the case's comparison rules. Your agent can follow another valid path through the world. Hue preserves observed facts and recorded query results while generating background records; the background's size is a heuristic, not a fidelity guarantee.

Missing essential evidence or evidence cut by a build limit blocks automatic publication. Optional background omissions remain visible as limitations. A published case records machine verification, its tier and its limitations; automatic publication does not record a human review. Hue does not run your agent before publishing, so run it against the case to verify your integration.

## Over the Hue MCP

With a **Read and write** connection, a coding agent can build the same case. Writes need the user's go-ahead; on an organization connection every call takes the case's project as `project_id`.

1. `get_trace` for the trace's current revision.
2. `add_case_conversion` with `trace_id`, `expected_trace_revision`, an `idempotency_key` and `run_was_correct`. Use `true` for a correct run and an optional reason in `outcome_intent`; use `false` and `outcome_intent` for what a wrong run should have done. Set `eval_set_id` to choose the destination, or omit it for a new eval set. Retrying the same request with the same idempotency key returns the original conversion.
3. New creates default to `publish_when_ready: true`. Poll `get_case_conversion` until it reports `status: "published"` or a reason to correct the draft. Automatic publication does not require reviewer acknowledgements or a `publish_case_conversion` call.
4. Read with `include_content: true` to inspect the task, criteria and any starting world. For corrections, use `update_case_conversion` with the latest `revision` as `expected_revision`; read the draft again after each write.

The `case_from_trace` MCP prompt follows this automatic route. To save an existing open eval-set draft afterwards, use **Save eval-set version** in Hue, `freeze_eval_set_version`, or `hue eval --save-version`. The [MCP tool reference](/agents/mcp-tools) lists each tool's arguments.

## Manual publication

Create with MCP `publish_when_ready: false` or REST `publishWhenReady: false` to keep a manual draft. Historical drafts without that field remain manual. REST creation uses `runWasCorrect` and `outcomeIntent` for the marking.

Read the task, criteria and any starting world before publishing. In the UI, the explicit **Publish** action confirms the displayed task, including a task read from a generic trace. Use the full review when the draft needs an edit or confirmation.

Over MCP, use `get_case_conversion` with `include_content: true`, then `update_case_conversion` to accept `reviewed_task` and `reviewed_criteria` in `accepted_assumptions`, with `accepted_criteria_digest`. Accept `authored_closed_world` only for a case with a world. Publish with `publish_case_conversion`, `name` and the latest `expected_revision` only when `ready: true`. Each write uses the revision of your latest read.

Manual MCP publication leaves the eval-set version open, including for a new eval set. Save it with **Save eval-set version**, `freeze_eval_set_version`, or `hue eval --save-version` before running the case.

## Tiers

A case publishes at a tier that says what its evaluators can verify. Run results report per tier. Newly generated world judges are required and score the new execution; historical advisory judge pins keep their policy. Answer-only cases retain their required answer judge. A failed required check fails the case; otherwise, a pending, unavailable or undecided required judge leaves the result **Inconclusive**.

| Tier | Meaning |
| --- | --- |
| T1 | World verified: every replayed call matched the rules' own answer, independently of the recording. |
| T2 | Some reads answered from the recording. |
| T3 | Partial, advisory. |
| T4 | Answer-only: required answer checks and the answer judge decide the case; no world is simulated. |

A trace that still needs correction (T5) is never published.

A published case is a reviewed task and a set of generated evaluators, built from one recorded trace. A query and model answer can become an answer-only case without an app simulation or a starting world. A trace with app calls can also pin a world; your agent then runs against a fresh copy with [`hue eval`](/evaluations/eval-ready-agent). This page covers both review paths. For what a world is, see [simulations](/evaluations/simulations).

## Traces that can become cases

Record the task and final answer with full content:

- Use `captureContent: true` in TypeScript or `capture_content=True` in Python. A trace exported without content cannot be reviewed into a case (`content_not_recorded`).
- For a trace with no tool calls, record the query as the root span's input and the reply as its output. **Answer-graded cases from plain traces** is on by default in project settings; an owner or admin can turn it off.
- For a trace with app calls, pass the MCP server identity on tool spans (`mcp:` on `hue.tool`) so the trace names the app each call reached. The case builds a world from supported app simulations or recorded tools; a call Hue cannot read or serve may prevent publication.

Case creation also refuses a trace that is still running (`running`; retry after it ends), evidence over 8 MiB, and a trace not recorded by Hue's SDK (`not_hue_sdk`) unless the project accepts generic sources, whose traces then need a full review (`generic_task_unreviewed`). Direct OTLP traces can qualify when the project accepts generic sources and their recorded content can be read. Metadata-only capture does not provide the task and answer a case needs.

## Answer-only cases

A support reply, summary or other model answer needs no simulated app when the selected turn made no tool calls. Hue pins the trace evidence, keeps the reviewed task and allowed earlier context, and generates checks for the answer. The draft has no starting world, app mirrors or replayed calls.

Mark a correct run **Yes** to generate checks from facts supported by the task and context. Mark it **No** and describe what should have happened to generate checks from that intent. Review the task, checks and any build limitations before publishing. The original answer is evaluator evidence, not a guaranteed correct answer, and is not given to the agent as part of the task.

Publication pins **Answer outcome** and the required **Answers the task** judge. A rerun must pass the required answer checks and judge to pass the case. An empty answer fails; an unavailable or undecided judge makes the result **Inconclusive**. A paraphrase can pass without matching the source answer word for word.

An answer-only case publishes at **T4**. Run it with the [agent command or a connected worker](/evaluations/eval-ready-agent#run-it); the agent receives the task and returns its answer without world setup. Cases that made tool calls use the app or recorded-tool path. A turn without a recorded answer cannot become an answer-only case; a turn that produced output files also needs a supported way to evaluate those files.

## In the Hue UI

1. Open **Traces** and open the trace.
2. Choose **Create case** and answer the one question: "Did the agent complete the task correctly?"
3. Choose **Build case**. Hue prepares the task and generated criteria. For app calls, it also builds the starting world.
4. Review the task and criteria. For a case with a world, also review the facts it rests on.
5. Choose **Publish case**. Publishing saves the eval-set version when Hue may; otherwise choose **Save eval-set version**.

## Over the Hue MCP

With a **Read and write** connection, a coding agent can run the same review. Writes need the user's go-ahead; on an organization connection every call takes the case's project as `project_id`.

1. `get_trace` for the trace's current revision.
2. `add_case_conversion` with `trace_id`, `expected_trace_revision` and an `idempotency_key`.
3. Poll `get_case_conversion` until the build finishes, then call it with `include_content: true` to read the task, criteria and any starting world you are about to accept. Every write below takes the `revision` of your latest read as `expected_revision`; read the draft again after each write before the next one.
4. If the draft asks "Was this run correct?", answer with `update_case_conversion` and `run_was_correct`.
5. Review the criteria and accept them: `update_case_conversion` with `reviewed_criteria` (`accepted_criteria_digest`) and `reviewed_task`. For a case with a world, also review `authored_closed_world`.
6. Publish only when `get_case_conversion` reports `ready: true`: `publish_case_conversion` with `name` and the current `expected_revision`. Readiness verifies the criteria and required review; an answer-only case has no world to replay.

The `case_from_trace` MCP prompt runs this sequence. To save the eval-set version afterwards, use **Save eval-set version** in Hue, the `freeze_eval_set_version` tool, or `hue eval --save-version`. The [MCP tool reference](/agents/mcp-tools) lists each tool's arguments.

## Tiers

A case publishes at a tier that says what its evaluators can verify. Run results report per tier. World cases have advisory judges; answer-only cases have a required answer judge.

| Tier | Meaning |
| --- | --- |
| T1 | World verified: every replayed call matched the rules' own answer, independently of the recording. |
| T2 | Some reads answered from the recording. |
| T3 | Partial, advisory. |
| T4 | Answer-only: required answer checks and the answer judge decide the case; no world is simulated. |

A trace that still needs a person (T5) is never published.

`@hue-run/sdk` includes the `hue` command. It stores a key you create in Hue, configures your coding agent for the [Hue MCP server](/agents/mcp-server), and runs a local agent against an eval set. Install it in the project where your agent lives:

<CodeGroup>
```sh npm
npm install @hue-run/sdk@0.14.0
```

```sh Bun
bun add @hue-run/sdk@0.14.0
```
</CodeGroup>

Run the commands from that project with `npx --yes --package @hue-run/sdk@0.14.0 hue …`. Always name the package: a bare `npx hue` can run an unrelated npm package called `hue`. Every command accepts `--help`.

## Store your key

Create a **Read and write** key in **Settings → Integrations & API keys** for the project you want to use, then run:

```sh
npx --yes --package @hue-run/sdk@0.14.0 hue login --gitignore
```

`hue login` prints the key settings page and opens it in your browser when a terminal is attached. It reads the key without echoing it, checks it against Hue, and stores it once as both `HUE_API_KEY` (for evaluations) and `HUE_MCP_KEY` (for your coding agent) in `./.env.hue`, together with `HUE_BASE_URL` and `HUE_MCP_URL`. `--gitignore` adds that file to `.gitignore`. Key values are never printed.

A **Read** or **Tracing only** key is refused before anything is stored, because it cannot run evaluations. See [Project keys](/quickstart#project-keys) for what each preset can do.

| Option | Effect |
| --- | --- |
| `--keys coding-agent` | Store only `HUE_MCP_KEY`. Accepts a **Read** key for an agent that should only inspect the project. |
| `--keys evaluations` | Store only `HUE_API_KEY`. |
| `--env-path PATH` | Write another file instead of `./.env.hue`, creating it when missing. |
| `--force` | Replace a different value already in the file. |
| `--origin URL` | Use another Hue origin, such as staging. |
| `--no-browser` | Print the settings page without opening it. |

`--env-file PATH` is also accepted for a file that already exists. Node.js 22 and 24 read `--env-file` from the whole command line, so when the file does not exist yet they exit with `node: <path>: not found` before `hue` runs; use `--env-path` to create a new file.

To revoke evaluation and agent access separately, run `--keys evaluations` and `--keys coding-agent` with two different keys.

## Connect your coding agent

```sh
npx --yes --package @hue-run/sdk@0.14.0 hue mcp install --client claude-code --auth oauth
```

`hue mcp install` writes a server named `hue` at `https://mcp.hue.run/mcp` for your client. Supported clients are `claude-code`, `codex`, `conductor`, `cursor`, `vscode`, `windsurf` and `gemini`. For `windsurf` it only prints the snippet; merge it into the configuration opened by Cascade's **… (Actions) → MCPs → Open MCP config file**. See the [Cascade MCP guide](https://docs.devin.ai/desktop/cascade/mcp) for that client's configuration. Add `--dry-run` to see the change first, or `--print` for the snippet only.

| Option | Effect |
| --- | --- |
| `--auth key` | The configuration reads the key from the `HUE_MCP_KEY` environment variable and never holds the key itself. The only choice for `cursor`, `vscode`, `windsurf` and `gemini`. |
| `--auth oauth` | The configuration holds only the URL, and you [sign in with Hue](/agents/mcp-server#sign-in-with-hue) in the client. Available for `claude-code`, `codex` and `conductor`, and their default. |
| `--client conductor` | Registers the server for Conductor's Claude Code (user scope) and Codex agents with each CLI on `PATH`, and signs in by default. Hue has not yet verified the complete signed-in Conductor flow end to end; if the tools do not load, run it again with `--auth key`. |
| `--read-only` | Selects a key and adds `?read_only=true` to its URL, so write tools are hidden whatever the key allows. A sign-in connection has **Read and write** access; use a **Read** key for read-only access. |
| `--project ID-OR-SLUG` | Pins the connection to one project, replaces any `project` already in the URL, and names the server `hue-<value>` so it can coexist with `hue`. Its tools omit `project_id`; `list_projects` returns only that project with `connection.pinned: true`. An unreachable pin is HTTP `404`, which signing in again does not fix. |
| `--toolsets NAMES` | Selects the [toolsets](/agents/mcp-server#choose-toolsets) the connection lists, such as `all` or `observe` for production reads, as `?toolsets=` on the URL, with a key or with sign-in. Without it, `claude-code`, `codex` and `conductor` select `all`, since they search their own tools; `cursor` selects `observe`; other clients list Hue's default, the production reads and `search_hue_tools`, which reaches every other tool. |
| `--scope user` | For `claude-code`, registers the server for all your projects instead of writing `.mcp.json`. |

Without `--auth`, `claude-code`, `codex` and `conductor` sign in with Hue, and the other clients use a key. `--read-only`, or `read_only=true` or `1` in `--url`, selects a key instead. `claude-code` and `codex` also keep the choice of the server's existing entry, in `./.mcp.json` or as `codex mcp get` reports it, so a rerun keeps a key and its `read_only`; for a new entry they use a key when `HUE_MCP_KEY` is set. For `codex`, when `codex` is on `PATH` but `codex mcp get` fails for a reason other than having no such server, the command asks you to pass `--auth` rather than guess. The command names its choice on stderr; pass `--auth` to replace an entry as given. Outside a terminal, such as in CI or a coding agent's shell tool, a default sign-in for `codex` or `conductor` prints the `codex mcp add` command instead of running it, because that command signs in at once and waits up to 5 minutes for the browser.

A Codex configuration sets `supports_parallel_tool_calls = true`, so Codex runs Hue's calls in parallel; `codex mcp add` cannot set it, so after registering with Codex the command names the line to add to `~/.codex/config.toml`. A printed sign-in TOML block keeps its URL bare and sends project and toolset selections as `X-Hue-MCP-Project` and `X-Hue-MCP-Toolsets` headers.

MCP arguments and results use the product object's name: for example, evaluation tools use `eval_set_id`, `eval_set_version_id`, `eval_set_case_id`, `evaluator_version_id`, `run_id`, `scoring_run_id` and `scoring_item_id`. Their list results are `eval_sets`, `evaluators`, `runs`, `scoring_runs` and `cases`; a row's own identifier remains `id`.

With a key, export `HUE_MCP_KEY` in the shell that starts your client; an app started from the Dock or a launcher does not see that shell's variables. Then ask the agent to call `list_projects` and `get_project_context` to confirm which project it reached. The [MCP guide](/agents/mcp-server) covers connection settings, verification and what the server can do.

## Run an evaluation

`hue eval` runs your agent locally against a published case or a saved eval set and prints Hue's verdicts. Your agent, prompts and model credentials stay on your machine. It uses `HUE_API_KEY` from `--env-file` (or its alias `--env-path`). Start the agent's own command with `--command`, after the one-time change in [Evaluation setup](/evaluations/eval-ready-agent):

```sh
npx --yes --package @hue-run/sdk@0.14.0 --package "zod@^4.6.5" hue eval --case "<name|id|url>" --command "<start command>" --env-file .env.hue
npx --yes --package @hue-run/sdk@0.14.0 --package "zod@^4.6.5" hue eval --worker --command "<start command>" --revision "<new-agent-revision>" --env-file .env.hue
```

The two `--package` flags put the CLI and its `zod` peer in npx's cache, so the agent's repository gains no package.json or dependency; without the second, `hue eval` exits with `hue eval needs zod`, even for `--help`, and installing zod in the project does not help when the SDK itself is not installed there. Always pin the version: in a project that already depends on `@hue-run/sdk`, an unpinned `--package @hue-run/sdk` runs that local, possibly older, copy. `hue eval` needs Node.js 22 or 24, even for a Python agent.

`--command` starts the command once per case with `{"inputs","config"}` as JSON on stdin and reads the answer from stdout. For a case with a simulated world, the command receives the world's variables; the eval-ready guide lists them under [Run it](/evaluations/eval-ready-agent#run-it) and shows the one committed helper that reads them, so the agent reaches each app through Hue's mirror with its own production client and never receives Hue-native tools. Only the current case's world sets those variables: a value inherited from your environment never reaches the command. A direct case has no simulated world: it sets `HUE_EXECUTION_ID` and case variables without a world token, app mirrors or MCP connection. Skip optional app initialization and fail closed if the agent needs a missing app connection. `HUE_CASE_INPUTS` names the inputs file, the case's input files are under `files/<role>/`, and every file the command writes to `HUE_CASE_OUTPUT_DIR` is uploaded as a generated file for grading. A one-shot direct case starts in that private case directory, so use an absolute entry-point path; a command worker keeps the directory where you started the CLI for both direct and world cases. The command inherits your environment except Hue's own credentials: `HUE_API_KEY`, `HUE_MCP_KEY` and any other variable holding a Hue key are removed unless you pass `--allow-hue-credentials`, so your model keys and settings still reach the agent but the project key does not.

`--worker` registers your agent so runs started from Hue, from the **Run** button or the `launch_local_run` MCP tool, execute on your machine with the same handoff. In TypeScript 0.13.2, command workers register both `direct:v1` and `environment:v1`, so one worker can run answer-only cases, world cases or an eval set containing both. Use a new `--revision` when upgrading an existing worker: a registered revision's capabilities cannot change.

| Flag | Meaning |
| --- | --- |
| `--case <name\|id\|url>` | Run one published case. |
| `--set <name\|id\|url>` | Run a saved eval set; needs `--scorer` or `--scorer-version`. |
| `--save-version` | Freeze an unsaved eval-set version before running. |
| `--command "<shell command>"` | Start the agent's own command per case. |
| `--worker` | Register the agent and execute runs launched from Hue. |
| `--json` | Print one JSON document on stdout; progress goes to stderr. |
| `--wait <seconds>` | Verdict wait after the run finishes (default 300). |
| `--timeout <seconds>` | Per-case `--command` timeout (default 600). |
| `--concurrency <n>` | Cases in flight, 1 to 64 (default 1). |
| `--baseline <run id\|url>` | Compare verdicts with a previous run. |
| `--trace-not-accepted fail_case\|pending` | What to do with a case whose telemetry Hue did not accept in time (default `fail_case`). |
| `--checkpoint-dir <path>` | Private checkpoint directory (default `.hue/eval/<agent-key>`; add `.hue/` to `.gitignore`). |
| `--capability <value>` | Extra worker capability, repeatable, such as `environment-files:v1` and `input:pdf`. |
| `--no-output` | One-shot: do not store case outputs, error messages and explanations. |
| `--content` | Explicitly enable telemetry content capture (the default). |
| `--no-content` | Opt out of telemetry content capture. |
| `--allow-hue-credentials` | Keep `HUE_API_KEY` and other Hue credentials in the `--command` child. |
| `--revision <id>` | The agent revision under test (default `AGENT_REVISION`, git `HEAD` or `dev`). |

One-shot exit codes: 0 every case passed; 1 a case failed, errored, is inconclusive or is incomplete; 2 usage error; 130 interrupted. `hue eval --help` lists every flag.

Since TypeScript 0.10.0, one-shot runs store case outputs, target error messages and explanations by default, as workers already do. Trace content capture is on by default; `--no-content` opts out. Earlier SDK versions require `--content` to enable it. Use `--no-output` to omit result content from a one-shot run, or `--no-output --no-content` to omit both results and telemetry content. Resume an older metadata-only run with `--no-content` and its original output policy. A command's stdout becomes its stored answer, with credentials handed to it by `hue eval` redacted; keep credentials and debug logs out of stdout. Generated files are uploaded regardless of `--no-output` and are not fully redacted, so never write credentials into them.

An evaluator that does not apply to a case shows `n/a` and neither passes nor fails it. A case with no applicable pinned evaluator is an error.

A TypeScript adapter file (`./hue-agent.ts` exporting `runMyAgent(inputs, context)`) is the in-process alternative. It runs inside `hue eval`'s own process, where `HUE_WORLD_TOKEN` and `HUE_EXECUTION_ID` are not set, so pass the execution context to the helper. A world-only adapter throws when `context.world` is missing, then passes `context.world.env` as the helper's environment argument or spawns the agent with `agentEnvironment(context.world)`. A direct adapter receives `context.mode: "direct"` and `context.executionId`; pass `{ HUE_EXECUTION_ID: context.executionId }` to the helper and skip app connections. Adapter-file workers register world support by default; opt into direct cases with `--capability direct:v1` only after handling that context. Never set `process.env` yourself: with `--concurrency` above 1 it leaks one case's world into another. See [simulations](/evaluations/simulations) for what the adapter receives and the [TypeScript reference](/reference/typescript) for the underlying current local-run APIs.

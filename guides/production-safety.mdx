Keep tracing best effort in a serving application: an outage should reduce observability, not prevent an answer. Hue follows OpenTelemetry's [runtime error containment](https://opentelemetry.io/docs/specs/otel/error-handling/) and [bounded-resource principles](https://opentelemetry.io/docs/specs/otel/performance/).

Use a **Tracing only** project service key for these serving examples. A **Read and write** key is necessary only when the same process also calls evaluation APIs; it can also read project data, so keep it off production servers.

The SDKs suppress their export traffic from OpenTelemetry instrumentation. If Python's suppression key is unavailable, Hue warns once and exports without it while its queues still ignore export work. Snapshot boundaries reject unsupported values; TypeScript also handles Proxies and typed bytes without bypassing queue budgets. Verify your dependency and instrumentor combination in CI.

<Note>
The APIs below require TypeScript `@hue-run/sdk >= 0.1.5` or Python `hue-run >= 0.1.3`. Confirm the installed version before using them. Older SDKs can propagate capture or lifecycle errors.
</Note>

## Separate setup verification from serving requests

Run the strict [quickstart](/quickstart), connection check and [trace receipt verification](/sdks/typescript#verify-stored-trace-evidence) during installation or a diagnostic command. They deliberately fail when Hue is unavailable; never make readiness or a customer response depend on them.

Create one client per serving process with the safe constructor and background export. Use safe lifecycle methods at the lifecycle boundary; never rerun an agent after a telemetry error because tools may have caused side effects.

`existingAgent` and `existing_agent` stand for your application function. Register shutdown in the process hook, not after client creation. For serverless requests, use `flushSafe` or `force_flush_safe` in the supported after-response lifecycle with a fitting deadline; do not shut down a shared provider per request.

## Failure behavior

Hue omits unsafe content, including oversized JSON or failing redactors, and records an instrumentation failure while preserving the callback's result and error. Safe initialization returns a disabled client on setup failure; disabled helpers still execute application work.

Python redactors receive detached copies. Hue snapshots helper content and the redactor's return value; each snapshot allows 1 MiB, depth 64 and 65,536 visited values/keys. Cycles, custom objects or subclasses, non-finite numbers, integers above 14,000 bits and over-budget inputs are omitted without calling the redactor. The final redacted JSON field is 256 KiB. Redactors must be deterministic and free of external side effects.

Safe lifecycle methods return failure results instead of raising. A timeout bounds the wait but does not prove delivery or undo an in-flight request. `createHue` / `Hue`, connection checks, verification and strict lifecycle methods remain diagnostic APIs and can reject configuration or report delivery failures.

Queues have both record and byte limits, including in-flight records. TypeScript's default byte budget is 8 MiB shared by traces and logs; Python's is 8 MiB per signal. Byte accounting bounds queued telemetry, not total process RSS. OTel objects, serialization, dependency code and application payloads consume additional memory. Overflow drops telemetry and updates counters; it never retries the agent's business operation.

Network export has bounded retry work. Python retains one worker per signal; an OS-blocked call can outlive the wait and retain one encoded request up to 1 MiB per signal outside queue counters. Later records queue within limits. Shutdown counts discarded records; process kill, full queues, disabled clients and exporter failures can lose telemetry. There is no disk spool or delivery guarantee.

No in-process library can prevent termination, OOM, event-loop stalls or third-party hooks. Keep redactors fast, deterministic and offline; other instrumentors retain their behavior. Safe construction cannot catch import or dependency failures before it runs, so verify startup in CI or load tracing behind an optional guarded integration.

## Kill switch and monitoring

The snippets read `HUE_TRACING_ENABLED`; set it to `false` and restart to bypass Hue without changing application code. It is not a remote flag. Strict constructors also accept `enabled: false` / `enabled=False`; a disabled client needs neither a key nor capture settings.

Inspect TypeScript's `hue.transport.getReport()` and Python's `hue.export_status` for failures, drops, pending bytes and exports. Counters are cumulative; pending bytes and records are current gauges. Emit only sanitized counts and status, never credentials, content or raw provider exceptions, and do not send health signals only through Hue.

Before rollout, test your real entry point against a loopback receiver that returns 503, rejects its key, delays its response and exceeds queue capacity. Verify that each tool runs once, results and errors match an uninstrumented request, and shutdown meets your deadline. Start with a small canary.

## Capture, titles and retention

The snippets capture content when `HUE_CAPTURE_CONTENT` is unset. Hue can show and evaluate only recorded data, including prompts, responses and tool inputs and outputs. Set `HUE_CAPTURE_CONTENT=false` for metadata-only export; this does not disable redaction or credential scrubbing. Use the [redaction recipe](/guides/redaction) for email and custom field rules.

In metadata-only mode, both SDKs strip recognized third-party content attributes on Hue's export path, but custom keys pass through; configure third-party instrumentors separately.

Hue names each trace from its own recorded request text, or from a trace name the producer set, inside Hue. Naming sends nothing to a model provider and needs no setting.

Telemetry retention is configured per project. A policy removes eligible older traces by periodic sweep; without one, telemetry does not expire automatically. Saved snapshots retain evidence after the source trace expires and need separate deletion; archiving does not delete data. Quotas protect admission, not retention.

## What Hue computes from your traces

Hue assesses stored traces, and some settings send recorded conversation text to a model. Align them with your capture policy. Owners/admins change trace-check consent in **Settings → Trace checks** and other settings in **Settings → Projects → Edit project**; MCP uses `set_trace_checks_consent` and `update_project`. Both require **Read and write** access and owner/admin authority.

| Setting | Default | What it does and sends |
| --- | --- | --- |
| **Trace findings** | On | Reads each ended trace's recorded spans inside Hue for rule findings, such as a tool error with no later success, and sets the trace's attention state. Nothing leaves Hue. |
| **AI trace findings** | On | Once a trace has ended or stalled, sends its latest user request, up to eight earlier conversation turns and the final reply to TypeSafe's decision model for typed judgments about the reply. It never sends tool arguments, results, files or metadata. Turning it off stops new judgments. |
| **AI intent classification** | On | Once the project publishes an intent taxonomy, sends excerpts of each trace's conversation to TypeSafe to sort traces by task type. |
| **AI request judges** | Off | Lets Hue's request judges send each request's text, earlier dialogue, handoffs to sub-agents, tool and skill inputs and outputs, and replies to TypeSafe's decision model to judge delegation, scope and answers, for the answers `get_request_answer` reports over MCP. Hue judges a project's requests only after it has set up request answers for that project. Turning it off stops new judgments. |
| **AI trace builds** | On | When someone builds a case or environment from a trace, sends redacted trace content and supplied context to models to populate the world, build and check the case, suggest criteria and calibrate judges. Turning it off stops new model calls for these builds. The MCP setting is `ai_case_conversion_suggestions`. |
| Trace-check consent | Off | Trace checks run only after a project gives this separate consent and activates a version. They then send bounded recorded requests, replies, delegation instructions, tool outputs and reduced context to the trace-check model through the Vercel AI Gateway. Withdrawing consent stops new model work. |

Traces from scoring runs are not assessed. The [production investigation guide](/agents/investigate-production#data-model) describes the attention states, findings, trace checks and intents that these settings produce.

## Ingestion limits

The default project allowance for customer telemetry uploads is 600 ingestion requests, 20,000 new records and 32 MiB of logical payload per one-minute window. Uploaded spans and logs share it. Hue's internally generated managed-evaluation root spans use a separate persistence path, so exhausting an upload allowance cannot prevent a completed managed job from recording its own orchestration evidence. That internal path retains tenant checks, transaction deadlines, trace limits and deduplication; an uploaded attribute or header cannot select it. The first window starts with an admitted request; after 60 seconds, the next request reservation or final evidence charge starts a new window. Requests count at admission; records and payload count at their final storage charge. Decoded authenticated attempts, including failed writes and exact retries, consume request allowance; exact retries do not consume additional record or payload allowance. Temporary admission limits return 429 or 503 with `Retry-After`; client queues can still overflow during a long outage.

Tracing authentication and storage use a separate bounded database pool from ordinary application queries. Naming a trace that a page finds unnamed also uses that pool, at most thirty traces per visit and one at a time; a failure leaves the trace unnamed until a later visit, so completed uploads never accumulate an unbounded naming queue.

These are protective limits, not a throughput SLA. Ask Hue to size your project's allowance for your expected instances, requests per minute, spans per request and average payload. Measure latency and resource overhead with your application's expected payload and concurrency. Do not assume local benchmark results establish production capacity.

If longer outage buffering is required, consider a separately operated OpenTelemetry Collector with explicit memory, queue and storage limits. A durable queue has its own disk and retention failure modes; it does not remove instrumentation overhead inside your application. See OpenTelemetry's [Collector resilience guidance](https://opentelemetry.io/docs/collector/resiliency/).

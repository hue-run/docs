  **Setting up Hue yourself?** Copy this prompt into your coding agent, such as Claude Code, Cursor or Codex, from your application's repository. The rest of this page is written for the agent.

  ```text Prompt wrap
  Set up Hue in this project. Use curl to read https://docs.hue.run/guides/agent-setup.md and follow it, and show me the plan before you change anything. If you can't open it, stop and tell me why.
  ```

  Your agent shows you its plan and asks you to create a **Read and write** API key in Hue and store it yourself, so the key never goes into the chat. It then adds tracing, verifies a real request and connects the Hue MCP server, which your agent can use once you restart it.

## 1. Get your Hue API key

This setup uses one **Read and write** project key, stored as both `HUE_API_KEY` and `HUE_MCP_KEY`. It sends traces, checks what Hue stored, runs evaluations and connects the [Hue MCP server](/agents/mcp-server).

First find how the application already provides local secrets, without reading any values: an ignored env file it loads (such as `.env.local` or `.env`), or a secret manager that injects variables into commands (such as Doppler, 1Password or Infisical). If that workflow already provides a **Read and write** key as both `HUE_API_KEY` and `HUE_MCP_KEY`, go to step 2. An existing `HUE_API_KEY` may be a **Tracing only** key; ask the user which preset it is. If it is **Read and write** but `HUE_MCP_KEY` is missing, ask the user to add `HUE_MCP_KEY` with the same value, then go to step 2.

Otherwise, tell the user, in this wording or close to it:

> Hue needs a **Read and write** API key from your Hue account. You create and store it yourself, so please don't paste it into this chat.
>
> 1. Sign in at https://app.hue.run, select the project that should receive this application's traces, open **Settings → Integrations & API keys** (https://app.hue.run/settings/integrations) and create a **Read and write** key. Members ask an owner or admin for one.
> 2. Store it as `HUE_API_KEY` and `HUE_MCP_KEY` in your secret manager, or run this in your own terminal from the repository root and paste the key at its hidden prompt: `npx --yes --package @hue-run/sdk@0.10.0 hue login --gitignore`
> 3. Tell me when it's stored. You don't need to run the next steps it prints; I'll do those.
>
> Don't have a Hue account yet? The Hue team sets up accounts: email founders@hue.run or book a time at https://calendar.notion.so/meet/akethini/hue. When your account is ready, paste the setup prompt again.

Don't run `hue login` yourself: it waits for the key at a hidden prompt. Never print, log or commit the key, and wait until the user says it's stored.

`hue login` checks the key against Hue, writes both variables to `.env.hue` and adds the file to `.gitignore` if it isn't ignored yet. It refuses a **Read** or **Tracing only** key and never prints the key. If the application loads another ignored env file, add `--env-path` with that file's path to the command in your message; add `--force` if the file already holds a different `HUE_API_KEY` or `HUE_MCP_KEY`.

No Node.js? The user skips the command and adds `HUE_API_KEY=` and `HUE_MCP_KEY=` lines with the key to an ignored env file in an editor.

## 2. Check the key

If the user ran `hue login` and it printed `Stored the key`, it has already checked the key. It also printed the key's project (`Evaluations access accepted for project "<name>"`): ask the user to confirm that is the project they intended, then go to step 3. Otherwise run this check without echoing the key. It sends the key only to app.hue.run and prints the key's project, not the key:

```sh
curl -s -w "\n%{http_code}\n" -H "Authorization: Bearer $HUE_API_KEY" https://app.hue.run/api/v1/projects/current
```

Load `HUE_API_KEY` the same way the application loads its environment, and wrap the command in `sh -c '…'` so the variable is expanded only after it is loaded. For example, use the secret manager's runner (`doppler run -- sh -c '…'`), `npx dotenv-cli -e <env-file> -- sh -c '…'` in a Node project or `uv run --env-file <env-file> -- sh -c '…'` in a uv project, where `<env-file>` is the file the key is in, such as `.env.local` or `.env.hue`.

This check sends no telemetry. `200` means the key works: tell the user the project `name` in the response and continue once they confirm it is the intended project. If it isn't, they create a key in the right project and store it again. `401` means the key is missing, mistyped or revoked: ask the user to check it, or create a new one and store it again, then check again. If the user can't sign in to Hue, they don't have an account yet: share the "Don't have a Hue account yet?" line from the step 1 message.

## 3. Add tracing

Use curl to read [Hue's skill](https://docs.hue.run/skill.md) on this site and follow it from **Choose the integration** through **Verify delivery** for the application's language and framework. Its **Get a Hue API key** section is already done. Hold its **Handoff** and come back here for step 4. The skill covers installing the SDK, choosing a capture policy, isolating serving requests from Hue and verifying a real request.

Set this up for complete traces. Hue can only show and evaluate what a trace records, so in the plan you show the user, recommend content capture (`captureContent: true` in TypeScript, `capture_content=True` in Python) and say that it sends prompts, responses and tool inputs and outputs to Hue. The user's go-ahead authorizes it under the skill's capture rule. If they decline, or an existing application policy forbids sending that content to another service, use metadata-only capture. Keep redaction and credential filtering either way. Instrument every request path that calls a model or tool, with model and tool child spans and the application's session identifier, not only the request you verify.

If the application already uses Langfuse or another OpenTelemetry destination, follow [Keep Langfuse and add Hue](/integrations/opentelemetry#keep-langfuse-and-add-hue). Add the second processor where the existing provider is constructed, preserve the existing AI SDK integration, and verify the same controlled request in both destinations. Do not upgrade the framework merely to add an exporter.

The SDKs don't load env files, so run the application through the same workflow as the check, for example its existing env loading, `node --env-file=<env-file>`, `uv run --env-file <env-file>` or the secret manager's runner, and keep reading `HUE_API_KEY` from the environment in code.

Keep the **Read and write** key on development machines. Before the application runs on a production server, tell the user to create a separate **Tracing only** key for that server's secret store; production code reads it from the same `HUE_API_KEY` variable.

## 4. Connect the Hue MCP server

This is the last step because most clients load a new MCP server only when they start. From the repository root, run this command, where `<client>` is `claude-code`, `codex`, `cursor`, `vscode`, `windsurf` or `gemini`:

```sh
npx --yes --package @hue-run/sdk@0.10.0 hue mcp install --client <client>
```

The command writes a server named `hue` that references `HUE_MCP_KEY`; it never writes the key. `.mcp.json` (Claude Code) and `.cursor/mcp.json` (Cursor) are safe to commit, and each teammate then needs their own key. For Codex, the command runs `codex mcp add`, which writes `~/.codex/config.toml`; if your sandbox blocks that, ask the user to approve it. VS Code prompts for the key when the server starts, and for Windsurf the command prints a snippet to merge into the file it names. Without Node.js, use the key instructions for the user's client in [Connect your client](/agents/mcp-server#connect-your-client); for a client without its own tab there, such as VS Code, Windsurf or Gemini CLI, use the **Any MCP client** tab's project-key settings.

If the user prefers browser sign-in, or the client can't send a key, follow [sign in with Hue](/agents/mcp-server#sign-in-with-hue-instead-of-a-key) instead; the client then holds no key.

The user restarts the client to load the server, so finish with one message that gives the user:

1. Your summary, in the form of the skill's **Handoff**. You have just configured the MCP server, so leave out the handoff's offer to connect it.
2. How to restart the client with the key. Load the key into the shell that starts the client, for example with `set -a; . ./.env.hue; set +a` for the env file the key is in, or start the client through the secret manager's runner. Then restart it from that shell: `claude --continue` for Claude Code, approving the `hue` server when asked; `codex resume --last` for Codex; or quit Cursor, reopen it with `cursor .` and turn on **hue** in its MCP settings. Restart any other client from that shell.
3. The prompt to send after the restart: `Use the Hue MCP: call list_projects and confirm which project to inspect. Then call get_project_context and show its 5 most recent error traces with links. For an organization connection, pass the project's id as project_id on each call after list_projects.`
4. What they can ask next, for example "What needs attention in the last 24 hours, and why?". [Investigate production](/agents/investigate-production) has the tool sequences for those questions.
5. Optionally, that they can keep the Hue skill in the project with `npx skills add hue-run/hue-sdk --skill hue`.

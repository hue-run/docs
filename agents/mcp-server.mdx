The Hue project-data MCP server is a hosted [Model Context Protocol](https://modelcontextprotocol.io) server at `https://mcp.hue.run/mcp`. There is nothing to install. Each connection reaches one project: **Read** access searches and inspects its data, such as traces, evaluations and cases, and **Read and write** access also changes project data. Billing and plan changes stay in Settings. `https://docs.hue.run/mcp` is a separate documentation-only server and cannot read your project.

## Quick start

1. Choose your client below and add `https://mcp.hue.run/mcp`. For **sign-in with Hue**, leave out API keys and custom headers.
2. When the client opens Hue, sign in with your verified account, select one project and approve **Read**. You must belong to that project's organization. Choose **Read and write** only if the agent should change project data.
3. Refresh the client's MCP status or start a new session, then [verify the connection](#verify-the-connection) by reading a trace through the agent.

Already have a project key, or using a client without sign-in support? [Prepare the key](#connect-with-a-project-key), then use your client's key instructions below. A **Tracing only** key cannot connect to this MCP server.

## Sign in with Hue instead of a key

Sign-in uses OAuth and requires no project key. Your account must be verified and an actual member of the project's organization; any member can approve a connection, without an owner or admin role. If you were invited, accept the invitation in Hue first, then connect again. Only active projects appear. Administrative visibility without membership does not grant access to a connected app.

Each approval covers one project and one access level. Check the signed-in account and project on the consent page before approving. Choose **Read** for inspection. To change projects, disconnect and reconnect the app.

Leave out the `Authorization` header and any bearer-token environment-variable setting when signing in. An old key entry can suppress sign-in or carry a failing header into authorization. Replace it using the instructions in your [client's tab](#connect-your-client).

<Accordion title="Access, expiry and disconnecting">
  - **Read** is selected by default. Choose **Read and write** if the client should write project data; write tools become available within your current organization role; `add_api_key` is never available. For a read-only connection, choose **Read** and leave `?read_only=true` off the URL.
  - The client receives access tokens that last 10 minutes and refreshes them automatically. Your approval lasts 30 days from when you connect; refreshing never extends it, so sign in again after that.
  - The connection acts for you. Writes are attributed to you, and owner- or admin-only tools check your current role: revoking keys, changing project settings or trace checks, archiving eval sets and evaluators, changing the judge alignment bar, registering managed targets and publishing the intent taxonomy. A connected app can never create project keys with `add_api_key`.
  - Sign-in covers the MCP server only. The SDKs and REST API still need a project key.
  - **Settings → Connected apps** lists your connections and disconnects them; owners and admins see and disconnect everyone's in the organization. Resetting your password or signing out everywhere disconnects every app you approved, and removal from the organization or an archived project ends the connection too.
</Accordion>

## Connect with a project key

1. An owner or admin creates a **Read** key, or a **Read and write** key if the agent should change project data, in **Settings → Integrations & API keys**. Save the key in your secret manager; it is shown once. Keep it separate from the application's **Tracing only** key.
2. For clients that read `HUE_MCP_KEY`, export the key alone, without `Bearer `, from your secret manager into the shell that starts the client. If your client offers a secure credential prompt, use that instead.
3. Follow your [client's tab](#connect-your-client), restart it from that shell and approve **hue** if asked. Desktop apps started from the Dock or a launcher do not inherit a terminal's variables.

Never put the key in application code, shared configuration or a prompt. See [project keys](/guides/project-keys) for access and rotation.

<Visibility for="agents">
  **If you are a coding agent:** reference `HUE_MCP_KEY` and never ask the user to paste the key. Adding configuration alone does not prove that the client connected. If the current session cannot load the server, use the [key check](#verify-the-connection), then ask the user to restart and [verify through the client](#verify-the-connection). For sign-in, let the user complete browser consent; do not request passwords or tokens.
</Visibility>

### Let your coding agent set it up

For a client that supports environment-variable references, paste this into your coding agent, started from a shell where `HUE_MCP_KEY` is exported. If your client uses a secure credential prompt, configure the key there instead.

```text Prompt wrap
Connect me to the Hue MCP server.

It is a remote MCP server (Streamable HTTP) at https://mcp.hue.run/mcp. Authenticate with a bearer token read from the HUE_MCP_KEY environment variable — reference the variable, do not write the key into a config file.

Register it under the name "hue" using whatever MCP configuration my client uses, then call get_project_context and tell me which Hue project it reached.
```

Most clients load a new server only when they start, and Claude Code and Cursor also ask you to approve it, so the agent usually can't call `get_project_context` in the session that added `hue`. Restart the client from the same shell, approve **hue** if asked, and ask again. If the agent asks you to paste the key, point it at `HUE_MCP_KEY` instead.

## Verify the connection

Ask the agent in the client you just connected:

```text
Use the Hue MCP: call get_project_context, then show my 5 most recent error traces with links.
```

Then ask it to call `get_trace` for one of the returned trace IDs. If there are no error traces, ask `search_traces` for recent traces without an error filter. An empty result is not an authentication failure; use a project with a known test trace to verify the full read path.

A successful check names the intended project and returns that project's trace through the MCP tool calls. A saved configuration or a **Connected** status alone does not establish that those calls work.

`get_project_context` returns the project the connection reaches and what the credential can do. `can_write` is `true` when write tools are available; `read_only` reports only the `?read_only=true` URL flag, so a **Read** key shows `read_only: false` together with `can_write: false`, and `write_preset` names the access that writing needs, not the access you have. If it reports a different project than you expected, the key was created in another project, or you approved another project at sign-in.

To check a key without an MCP client, send one tool call from a shell where `HUE_MCP_KEY` is exported. This is the check to use when a client shows only a short status, and the non-interactive check for a coding agent. It proves the key, not the client's configuration:

```sh
printf 'Authorization: Bearer %s\n' "$HUE_MCP_KEY" | \
curl -sS -w '\nHTTP %{http_code}\n' -X POST https://mcp.hue.run/mcp \
  -H @- \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"get_project_context","arguments":{}}}'
```

The shell's `printf` builtin sends the header through standard input, keeping the expanded key out of curl's process arguments. `HTTP 200` with an `event: message` response that names your project means the key works. `401` means the key is missing, wrong, revoked or expired, and `403` means it is not a **Read** or **Read and write** key; the response body explains the refusal. The server needs both `Accept` types and answers `406` without them. It is stateless, so no session or `initialize` call is needed first.

## Troubleshooting

For key-based connections, the [curl check](#verify-the-connection) shows Hue's response when the client displays only a short status. Some clients treat any `401` as a request to sign in; fix or remove a failing key header before starting OAuth. For sign-in connections, use the client's authentication action and the sign-in rows below.

| Symptom | Cause | Fix |
| --- | --- | --- |
| Your organization or project is missing from the consent page | The signed-in account is unverified, has not accepted its organization invitation, is not a member, or the project is archived | Check the account shown on the page, verify your email and accept your invitation in Hue, then reconnect. Ask an organization owner or admin to check your membership and the project. Staff or administrative visibility alone is not membership. |
| The client reports missing OAuth metadata | The URL is wrong, a saved entry still targets an old endpoint, or discovery failed | Use `https://mcp.hue.run/mcp` without a custom authorization header, refresh the client's configuration and retry. If it persists, report the client/version and error text without tokens. |
| Consent succeeds but no Hue tools appear | The running agent session has not loaded the new connection | Refresh MCP status and start a new session, then run the verification above. In Conductor, check the configuration for the selected agent. |
| A Hue sign-in page opens, or the client shows **Needs authentication**, `Authentication required`, `requires_authentication` (Cursor), `The hue MCP server is not logged in` (Codex), although you configured a key | Hue refused the key. Usually `HUE_MCP_KEY` is unset or empty where the client started, the header lacks `Bearer ` or repeats it, the key is in another header such as `x-api-key`, or the key is wrong or revoked. Also check that the saved configuration still holds the `${HUE_MCP_KEY}` reference rather than `Bearer` or the key (a CLI `--header` in double quotes), that no other `hue` entry without the header overrides it (Claude Code), and that Codex was added with `--bearer-token-env-var` | Run the curl check and match its message to the rows below. Export `HUE_MCP_KEY` in the shell that starts the client, restart the client, and send exactly `Authorization: Bearer <key>`. Don't finish a sign-in that opened because of a failing key: it fails too. |
| `Malformed initial access token Authorization header` or `Dynamic Client Registration rejected (HTTP 401) … Invalid initial access token` | The client tried to sign in and sent your failing key header along: the variable is unset or empty or already holds `Bearer `, or the key is wrong, a placeholder or an unexpanded `${…}` reference | Fix the key as in the row above, then restart the client. Or remove the header and sign in. |
| Codex reports `Environment variable HUE_MCP_KEY for MCP server 'hue' is not set` or `… is empty` | The variable is missing, empty or set without `export` in the shell that started Codex | Export the key in that shell and restart Codex. |
| `401` `The bearer token is not a Hue credential` | The client sent something other than a key: the reference itself, such as `${HUE_MCP_KEY}`, because the variable was unset or the syntax is not the client's, or a value with extra characters such as surrounding quotes | Set the variable to the key alone before starting the client, and use the client's syntax: `${HUE_MCP_KEY}` for Claude Code and `${env:HUE_MCP_KEY}` for Cursor. For other clients, follow their environment-variable or secret-storage syntax. Codex needs `bearer_token_env_var` and does not expand `${…}` in `http_headers`. |
| `401` `A valid project service key is required` | The key is wrong, truncated, revoked or expired | Copy the key again from your secret manager, or create a new one in **Settings → Integrations & API keys**. |
| `403` `This key cannot read project data` | The key is **Tracing only** or a legacy **Tracing and evaluations** or **Source capture (legacy)** key | Create a **Read** or **Read and write** key and configure it in your client. Or [sign in with Hue](#sign-in-with-hue-instead-of-a-key). |
| `Unexpected content type: text/html`, HTTP `404` or `MCP endpoint not found` | Wrong URL: the host root, `/api` without `/mcp`, or `/mcp` on `app.hue.run` | Use `https://mcp.hue.run/mcp` exactly. A trailing slash is fine. |
| `429` `Too many failed authentications for this key`, or `Too many requests. Please try again later.` while a client tries to sign in | Ten failed attempts with this key within a minute, often from another client with an old or truncated copy, or repeated sign-in attempts from a client whose key header keeps failing | Fix or stop that client, then wait a minute. Until then the correct key is refused too. |
| `503` with `Retry-After: 1` | The server is momentarily busy | Retry after a second. |
| The client reports `invalid HTTP header` | The stored key ends with a newline | Store the key without a trailing newline. |
| Cursor shows `not loaded (needs approval)` or `has not been approved` | Cursor has not approved the server, or `HUE_MCP_KEY` changed or became unset since you approved it | Check that `HUE_MCP_KEY` is exported and holds the key you intend, then turn on **hue** in Cursor's MCP settings, or run `cursor-agent mcp enable hue`. Cursor asks again after every change. |
| A client you connected by signing in shows **Needs authentication** or `The hue MCP server is not logged in` | The approval ended: 30 days passed, someone disconnected it in **Settings → Connected apps**, you reset your password or signed out everywhere, or you left the organization or the project was archived | Sign in again: `/mcp` → **Authenticate** in Claude Code, `codex mcp login hue`, or `cursor-agent mcp login hue`. |
| A tool call fails as an unknown tool | Write tools are hidden for **Read** access and for a URL with `?read_only=true`; [retired tool names](#retired-tool-names) are no longer served; a tool described in a development branch is not available until its platform release is deployed | Use a **Read and write** key without `?read_only=true`, approve **Read and write** at sign-in, or call the current tool name. Use the tools your connection's `tools/list` returns; an unknown tool is not evidence that the client should broaden its permissions. |

See [troubleshooting](/guides/troubleshooting#the-mcp-server-rejects-the-agent) for tracing problems that are not specific to MCP.

<Accordion title="Endpoints and protocol details">
  The project-data server is a dynamic Node.js route in Hue's main web application, not a separate data service. `https://app.hue.run/api/mcp` remains a supported compatibility alias. The `search_hue_docs` tool delegates documentation searches to the Mintlify-hosted documentation endpoint without changing the project-data server's authentication boundary.

  The server is stateless and accepts clients that start with `initialize` (MCP revisions up to 2025-11-25) as well as clients on the stateless 2026-07-28 revision, so clients need no extra flags. It accepts `POST` only. A `GET` with no `Authorization` header, or with a value that is not a Hue key or token, gets `401` with the sign-in challenge. A `GET` that carries any Hue key or token gets `405` with `Allow: POST`; the key is not checked. A request carrying `Mcp-Session-Id` gets `404`, because the server keeps no sessions. MCP clients handle these answers themselves.
</Accordion>

## What you can do

Every tool is scoped to the one project the connection reaches. Write tools need **Read and write** without `?read_only=true`. Ask before any write, and do not auto-approve write tools.

<AccordionGroup>
  <Accordion title="Investigate a failure">
    "Show the error traces from the last 24 hours", "open the slowest span of that trace", "what did the model see before it failed?" (recorded content requires `include_content: true` and the application must have captured it). Tools: `search_traces`, `get_trace`, `get_span`, `list_sessions`. Each trace reports a `state`: `running` while a span is still open, `stalled` when 15 minutes pass without new data and no end arrives, or `ended`. Only the TypeScript SDK 0.7.0 and Python SDK 0.4.0 or later report open spans, and only Hue and AI spans still open when their placeholder is exported, usually about 1.5 s after they start; other spans, including every span from other exporters, appear once they end.
  </Accordion>
  <Accordion title="Confirm delivery">
    "Did trace 0af7651916cd43dd8448eb211c80319c arrive with spans a and b, with model and usage recorded?" Tools: `verify_trace`.
  </Accordion>
  <Accordion title="Trace checks">
    Read the project's production trace checks with `list_trace_checks` and `get_trace_checks`, their results with `get_trace_check_results` (source excerpts require `include_content: true`), and coverage and request timing with `get_trace_check_summary`. Results are advisory, not evaluator scores. With **Read and write**, save a new draft version with `save_trace_checks`, set the separate consent to send recorded content to the trace-check model with `set_trace_checks_consent`, test a saved version on up to ten traces with `test_trace_checks`, turn automatic checks on or off with `activate_trace_checks` and `deactivate_trace_checks`, and queue recent traces for the active version with `reassess_trace_checks`. Through sign-in, only an owner or admin can make these changes.
  </Accordion>
  <Accordion title="Read evaluations">
    "List my eval sets", "show the cases in the latest version of the regression set", "summarize the last run and list the failing cases", "compare it against the baseline run". Tools: `list_eval_sets`, `get_eval_set`, `list_evaluators`, `get_evaluator`, `list_runs`, `get_run`, `list_run_items`, `get_run_item`, `get_run_execution`, `list_scoring_runs`, `get_scoring_run`, `list_environments`, `get_environment`.
  </Accordion>
  <Accordion title="Author evaluations">
    Create an eval set (`add_eval_set`), add cases (`add_eval_set_cases`), edit a draft (`update_eval_set`, `update_eval_set_case`, `delete_eval_set_case`, `add_eval_set_draft`), freeze it (`freeze_eval_set_version`), then pin evaluators (`add_evaluator`, `publish_evaluator`, `copy_evaluator`) and create a run (`add_run`). Record scoring results with `add_scoring_run` and `add_scoring_results`. Hide retired identities with `archive_eval_set`, `archive_evaluator` or `archive_environment`. Case execution can stay with the SDK, a managed run, a local agent, or `start_run_case` / `complete_run_case` / `finish_run`. Never auto-approve `add_*`, `update_*`, `delete_*`, `publish_*`, `freeze_*`, `archive_*` or `copy_*`.
  </Accordion>
  <Accordion title="Label and promote judges">
    Read scored judge results with their agree and disagree counts and your own label with `list_judge_results`, and a judge version's alignment, the project's alignment bar, promotion state and a comparison with another version with `get_judge_alignment`. With **Read and write**, label a result `agree` or `disagree` with `label_judge_result`, promote or demote a judge version with `set_judge_promotion`, rescore a new version on its judge's labeled executions and compare it with an earlier version with `check_judge_regression`, and change the project's alignment bar with `set_judge_alignment_bar`, which requires an owner or admin.
  </Accordion>
  <Accordion title="Author environments">
    `add_environment` and `publish_environment_version` create a simulated world a case can pin.
  </Accordion>
  <Accordion title="Reviewed cases">
    `list_cases` lists cases reviewed from traces, drafts and published, with links. `get_case` returns one case with its eval set, saved version, pinned outcome evaluator, environment and a ready run block for `launch_local_run` or `hue eval`; the reviewed task text is returned only with `include_content: true`.
  </Accordion>
  <Accordion title="Create a case from a trace">
    Requires **Read and write** without `?read_only=true`. In Hue, open the trace and choose **Create case** in the trace inspector, or choose **Create case** from **Suggested cases**. A coding agent runs the same review over MCP. `add_case_conversion` pins the trace into a draft case, and repeating the call with the same idempotency key returns the same draft. `get_case_conversion` reports readiness and findings, and returns the saved task, starting world and criteria only with `include_content: true`. `update_case_conversion` edits the draft, and `publish_case_conversion` publishes a ready draft into a new or existing eval set. `archive_case_conversion` abandons a draft; a published case can't be archived, but its eval set can. Before you publish, review the task and the starting world, and set success criteria independently of the recorded answer. A trace that is still running can't become a case. The REST endpoint `https://app.hue.run/api/v1/case-conversions` runs the same workflow. `list_cases` and `get_case` then read the case, whether it is a draft or published.
  </Accordion>
  <Accordion title="Intents">
    Read the taxonomy and buckets with `get_intent_taxonomy`, `get_intent_summary` and `list_intent_traces`. `save_intent_taxonomy` republishes categories and requires an owner or admin.
  </Accordion>
  <Accordion title="Managed and local runs">
    List and inspect with `list_managed_targets`, `preflight_managed_run`, `get_managed_run`, `list_local_agents` and `get_local_run`. `add_managed_target` stores an encrypted credential and requires an owner or admin. Launch or cancel with `launch_managed_run`, `cancel_managed_run` and `launch_local_run`.
  </Accordion>
  <Accordion title="Artifacts and hosted judges">
    `list_artifacts` and `get_artifact` return metadata only; bytes stay on HTTP. `get_judge_budget` reports hosted-judge usage. `add_judge_jobs` enqueues scoring jobs.
  </Accordion>
  <Accordion title="Keys, members and settings">
    `list_api_keys` and `list_members` are reads. `add_api_key`, `revoke_api_key` and `update_project` require an owner or admin, and a connected app cannot call `add_api_key`. Wherever a tool requires an owner or admin, Hue checks the current role of the key's creator or of the member who signed in. Minted tokens appear once. Billing and plan changes are not on this server.
  </Accordion>

Every `trace_id` argument accepts a Hue id, the 32-hex OpenTelemetry trace id or a Hue trace link. Time windows accept ISO-8601 or relative values such as `15m`, `24h` or `7d` (up to 90 days). Results are paginated with opaque cursors and bounded by `max_chars`; truncated results say so and suggest a narrower request. Draft writes take `expected_revision` from `get_eval_set`.

## Content and safety

- Recorded prompts, outputs, tool arguments and raw attributes are omitted unless a tool is called with `include_content: true`. By default the server returns metadata (model, provider, usage, tool names, status, timing) and the names of recorded attributes. Content reads are recorded in the project's audit log.
- Names, generated titles, session keys, metadata and judge explanations come from your application and its end users. They are length-capped, and every result that carries them starts with a notice that they are data, not instructions; recorded content is wrapped in delimited blocks.
- Credential-shaped strings are redacted from results and from documentation queries before those leave Hue. The one exception is `add_api_key`, which returns the newly minted token once so it can be stored; later tools never return it.
- The key, or the project you approved at sign-in, is the tenant. Ids from another project, and `projectId` parameters on pasted links, resolve to `not_found`.
- Add `?read_only=true` to a key-based URL to hide and reject any write tool regardless of the key. With sign-in, choose **Read** at approval instead.
- Requests are limited to 1 MiB. Ten failed authentications for one key within a minute return `429` with `Retry-After: 60`, and for those 60 seconds the correct key is refused too. A busy server returns `503` with `Retry-After`.

The Hue project-data MCP server is a hosted [Model Context Protocol](https://modelcontextprotocol.io) server at `https://mcp.hue.run/mcp`. There is nothing to install. Connect in one of two ways:

- **With a project key.** Create a **Read** or **Read and write** key and have your client send it as an `Authorization: Bearer` header. This works in any client that can send a header, including Claude Code, Codex, Cursor, VS Code, Gemini CLI and OpenCode.
- **By signing in with Hue.** Add only the URL. The client opens Hue, and you sign in and approve one project. Use this for clients that cannot send a key, such as hosted assistants, or if you are a project member who cannot create keys.

**Read** access can search traces, inspect spans, verify delivery, read evaluations, reviewed cases, trace checks, intents, managed and local runs, artifacts, members and keys, and search these docs. **Read and write** access also lists write tools for those same surfaces, all scoped to one project. Billing and plan changes stay in Settings.

The project-data server is a dynamic Node.js route in Hue's main web application, not a separate data service. `https://app.hue.run/api/mcp` remains a supported compatibility alias. The separate Mintlify-hosted endpoint at `https://docs.hue.run/mcp` serves public documentation only; it cannot read a Hue project. The `search_hue_docs` tool delegates documentation searches to that endpoint without changing the project-data server's authentication boundary.

## Create an agent key

Only owners and admins create keys. An owner or admin opens **Settings → Integrations & API keys**, chooses the project and creates a **Read** key, or a **Read and write** key if the agent should change project data. The dialog shows the key once, together with where it goes: the `HUE_MCP_KEY` variable and the MCP URL. Save it in your secret manager. Other members [sign in with Hue](#sign-in-with-hue-instead-of-a-key) instead.

Keep this key separate from the application's `HUE_API_KEY`, which uses **Tracing only**. A **Read** key cannot send telemetry or change project data; it can still read project data, including captured content when explicitly requested. Do not auto-approve write tools. The key should never be wired into application code or committed. See [project keys](/guides/project-keys).

### Make the key available

The key-based setups below, except VS Code and Claude Desktop, read the key from `HUE_MCP_KEY` when the client starts:

- Export `HUE_MCP_KEY` in the shell that starts the client, for example `export HUE_MCP_KEY="$(…)"` with your secret manager's read command inside `$(…)`, then start the client from that shell. Without `export` the client does not see the variable. A client that is already running does not see a new value until you restart it.
- Desktop apps started from the Dock, the Start menu or a launcher do not see variables exported in a terminal. Start the app from that terminal, or use the client's own secret prompt where it has one, as VS Code does.
- Set the variable to the key alone, without a `Bearer ` prefix, surrounding quote characters or a trailing newline. The client configuration adds `Bearer `.

## Connect your client

Paste this into your coding agent, started from a shell where `HUE_MCP_KEY` is exported. For VS Code and Claude Desktop, follow their tabs below instead: they keep the key in the client, not in a variable.

```text Prompt wrap
Connect me to the Hue MCP server.

It is a remote MCP server (Streamable HTTP) at https://mcp.hue.run/mcp. Authenticate with a bearer token read from the HUE_MCP_KEY environment variable — reference the variable, do not write the key into a config file.

Register it under the name "hue" using whatever MCP configuration my client uses, then call get_project_context and tell me which Hue project it reached.
```

Most clients load a new server only when they start, and Claude Code and Cursor also ask you to approve it, so the agent usually can't call `get_project_context` in the session that added `hue`. Restart the client from the same shell, approve **hue** if asked, and ask again. A `curl` call from the agent proves the key, not the client; the check at the end of each tab tests the client itself. If the agent asks you to paste the key, point it at `HUE_MCP_KEY` instead. If your client cannot send a header, [sign in with Hue](#sign-in-with-hue-instead-of-a-key).

Prefer to set it up yourself? The snippets below reference the key rather than contain it, except Claude Desktop's, which cannot read your shell's variables. Never paste a literal key into a configuration file that other people or tools can read. Each tab ends with a check that shows whether the client reached Hue.

Other clients need Streamable HTTP and a way to send `Authorization: Bearer <key>` on every request from their secret storage or an environment reference. Check the client's current configuration format before installing. A client that only runs local (stdio) servers can reach Hue through `mcp-remote`, as in the Claude Desktop tab. The server is stateless and accepts clients that start with `initialize` (MCP revisions up to 2025-11-25) as well as clients on the stateless 2026-07-28 revision, so clients need no extra flags. Use the canonical `https://mcp.hue.run/mcp` address for new configurations.

## Sign in with Hue instead of a key

Clients that support MCP authorization connect with the URL alone. On the first connection Hue answers that sign-in is required, and the client opens Hue in your browser. Sign in, choose one project, choose **Read** or **Read and write**, and approve. Any verified member of the project can connect this way; you do not need a key or an owner or admin role.

Leave out the `Authorization` header when you want to sign in. Claude Code never offers sign-in while a header is configured, and a client that opens sign-in because its key header failed carries that header into sign-in, which then fails. If a sign-in page opens although you configured a key, fix the key or remove the header.

**Claude Code.** Add the server, then run `/mcp` in Claude Code, select `hue` and choose **Authenticate**. This adds `hue` for the current project; add `--scope user` for all projects. Until you authenticate, `claude mcp get hue` shows `! Needs authentication`, which is expected.

```sh
claude mcp add --transport http hue https://mcp.hue.run/mcp
```

Claude Code keeps one `hue` entry per scope, and a local entry overrides project and user entries. To switch between a key and sign-in, run `claude mcp remove hue -s <scope>` with the scope `claude mcp get hue` reports, then add the other form. After you switch from sign-in to a key, new sessions can skip `hue` for about 15 minutes; run `/mcp` in a new session to confirm its tools are listed.

**Codex.** Add the server. `codex mcp add` opens Hue straight away, so run it in a terminal where you can use a browser; `codex mcp login hue` signs in again later:

```sh
codex mcp add hue --url https://mcp.hue.run/mcp
codex mcp login hue
```

**Cursor.** Add only the URL and approve the server as in the Cursor tab. Cursor then shows **Needs login** for `hue` (`requires_authentication` in the CLI); select it, or run `cursor-agent mcp login hue`.

```json .cursor/mcp.json
{
  "mcpServers": {
    "hue": {
      "url": "https://mcp.hue.run/mcp"
    }
  }
}
```

**Claude Desktop configuration file.** Give `mcp-remote` only the URL. It opens Hue in your browser the first time Claude Desktop starts it and reuses the approval after that. To change the project or access, disconnect the app in **Settings → Connected apps**, delete `mcp-remote`'s saved sign-in in `~/.mcp-auth`, and restart Claude Desktop:

```json claude_desktop_config.json
{
  "mcpServers": {
    "hue": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "https://mcp.hue.run/mcp"]
    }
  }
}
```

**Hosted assistants.** claude.ai, Claude Desktop's **Settings → Connectors** and ChatGPT developer mode accept only a URL and cannot send your own key. Add `https://mcp.hue.run/mcp` as a custom connector and sign in when it prompts you. Hue has not yet verified these hosted clients end to end.

How a sign-in connection works:

- **Read** is selected by default. Choose **Read and write** if the client should write project data; the client then lists every tool except `add_api_key`. For a read-only connection, choose **Read** and leave `?read_only=true` off the URL.
- The client receives access tokens that last 10 minutes and refreshes them automatically. Your approval lasts 30 days from when you connect; refreshing never extends it, so sign in again after that.
- The connection acts for you. Writes are attributed to you, and owner- or admin-only tools check your current role: revoking keys, changing project settings or trace checks, archiving eval sets and evaluators, registering managed targets and publishing the intent taxonomy. A connected app can never create project keys with `add_api_key`.
- Sign-in covers the MCP server only. The SDKs and REST API still need a project key.
- **Settings → Connected apps** lists your connections and disconnects them; owners and admins see and disconnect everyone's in the organization. Resetting your password or signing out everywhere disconnects every app you approved, and removal from the organization or an archived project ends the connection too.

## Verify the connection

Ask the agent:

```text
Use the Hue MCP: call get_project_context, then show my 5 most recent error traces with links.
```

`get_project_context` returns the project the connection reaches and what the credential can do. `can_write` is `true` when write tools are available. `read_only` reports only the `?read_only=true` URL flag, so a **Read** key shows `read_only: false` together with `can_write: false`, and `write_preset` names the access that writing needs, not the access you have. If it reports a different project than you expected, the key was created in another project, or you approved another project at sign-in.

To check a key without an MCP client, send one tool call from a shell where `HUE_MCP_KEY` is exported. Use this check whenever a client shows only a short status, and as the non-interactive check for a coding agent; it proves the key, not the client's configuration:

```sh
curl -sS -w '\nHTTP %{http_code}\n' -X POST https://mcp.hue.run/mcp \
  -H "Authorization: Bearer $HUE_MCP_KEY" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"get_project_context","arguments":{}}}'
```

`HTTP 200` with an `event: message` response that names your project means the key works. `401` means the key is missing, wrong, revoked or expired, and `403` means it is not a **Read** or **Read and write** key; the response body explains the refusal. The server needs both `Accept` types and answers `406` without them. It is stateless, so no session or `initialize` call is needed first.

## What you can do

**Investigate a failure.** "Show the error traces from the last 24 hours", "open the slowest span of that trace", "what did the model see before it failed?" (recorded content requires `include_content: true` and the application must have captured it). Tools: `search_traces`, `get_trace`, `get_span`, `list_sessions`. Each trace reports a `state`: `running` while a span is still open, `stalled` when 15 minutes pass without new data and no end arrives, or `ended`. Only the TypeScript SDK 0.7.0 and Python SDK 0.4.0 or later report open spans, and only Hue and AI spans still open when their placeholder is exported, usually about 1.5 s after they start; other spans, including every span from other exporters, appear once they end.

**Confirm delivery.** "Did trace 0af7651916cd43dd8448eb211c80319c arrive with spans a and b, with model and usage recorded?" Tools: `verify_trace`.

**Trace checks.** Read the project's production trace checks with `list_trace_checks` and `get_trace_checks`, their results with `get_trace_check_results` (source excerpts require `include_content: true`), and coverage and request timing with `get_trace_check_summary`. Results are advisory, not evaluator scores. With **Read and write**, save a new draft version with `save_trace_checks`, set the separate consent to send recorded content to the trace-check model with `set_trace_checks_consent`, test a saved version on up to ten traces with `test_trace_checks`, turn automatic checks on or off with `activate_trace_checks` and `deactivate_trace_checks`, and queue recent traces for the active version with `reassess_trace_checks`. Through sign-in, only an owner or admin can make these changes.

**Read evaluations.** "List my eval sets", "show the cases in the latest version of the regression set", "summarize the last run and list the failing cases", "compare it against the baseline run". Tools: `list_eval_sets`, `get_eval_set`, `list_evaluators`, `get_evaluator`, `list_runs`, `get_run`, `list_run_items`, `get_run_item`, `get_run_execution`, `list_scoring_runs`, `get_scoring_run`, `list_environments`, `get_environment`.

**Author evaluations.** Requires **Read and write** without `?read_only=true`. Create an eval set (`add_eval_set`), add cases (`add_eval_set_cases`), edit a draft (`update_eval_set`, `update_eval_set_case`, `delete_eval_set_case`, `add_eval_set_draft`), freeze it (`freeze_eval_set_version`), then pin evaluators (`add_evaluator`, `publish_evaluator`, `copy_evaluator`) and create a run (`add_run`). Record scoring results with `add_scoring_run` and `add_scoring_results`. Hide retired identities with `archive_eval_set`, `archive_evaluator` or `archive_environment`. Case execution can stay with the SDK, a managed run, a local agent, or `start_run_case` / `complete_run_case` / `finish_run`. Ask before any write; never auto-approve `add_*`, `update_*`, `delete_*`, `publish_*`, `freeze_*`, `archive_*` or `copy_*`.

**Author environments.** `add_environment` and `publish_environment_version` create a simulated world a case can pin.

**Reviewed cases.** `list_cases` lists cases reviewed from traces, drafts and published, with links. `get_case` returns one case with its eval set, saved version, pinned outcome evaluator, environment and a ready run block for `launch_local_run` or `hue eval`; the reviewed task text is returned only with `include_content: true`.

**Create a case from a trace.** Requires **Read and write** without `?read_only=true`. In Hue, open the trace and choose **Create case** in the trace inspector, or choose **Create case** from **Suggested cases**. A coding agent runs the same review over MCP. `add_case_conversion` pins the trace into a draft case, and repeating the call with the same idempotency key returns the same draft. `get_case_conversion` reports readiness and findings, and returns the saved task, starting world and criteria only with `include_content: true`. `update_case_conversion` edits the draft, and `publish_case_conversion` publishes a ready draft into a new or existing eval set. `archive_case_conversion` abandons a draft; a published case can't be archived, but its eval set can. Before you publish, review the task and the starting world, and set success criteria independently of the recorded answer. A trace that is still running can't become a case. The REST endpoint `https://app.hue.run/api/v1/case-conversions` runs the same workflow. `list_cases` and `get_case` then read the case, whether it is a draft or published.

**Intents.** Read the taxonomy and buckets with `get_intent_taxonomy`, `get_intent_summary` and `list_intent_traces`. `save_intent_taxonomy` republishes categories and requires an owner or admin.

**Managed and local runs.** List and inspect with `list_managed_targets`, `preflight_managed_run`, `get_managed_run`, `list_local_agents` and `get_local_run`. `add_managed_target` stores an encrypted credential and requires an owner or admin. Launch or cancel with `launch_managed_run`, `cancel_managed_run` and `launch_local_run`.

**Artifacts and hosted judges.** `list_artifacts` and `get_artifact` return metadata only; bytes stay on HTTP. `get_judge_budget` reports hosted-judge usage. `add_judge_jobs` enqueues scoring jobs.

**Keys, members and settings.** `list_api_keys` and `list_members` are reads. `add_api_key`, `revoke_api_key` and `update_project` require an owner or admin, and a connected app cannot call `add_api_key`. Wherever a tool requires an owner or admin, Hue checks the current role of the key's creator or of the member who signed in. Minted tokens appear once. Billing and plan changes are not on this server.

**Look things up.** "How do I flush spans in a Next.js streaming route?" Tools: `search_hue_docs`, `load_hue_guide` (`data-model`, `investigate`, `author`).

Every `trace_id` argument accepts a Hue id, the 32-hex OpenTelemetry trace id or a Hue trace link. Time windows accept ISO-8601 or relative values such as `15m`, `24h` or `7d` (up to 90 days). Results are paginated with opaque cursors and bounded by `max_chars`; truncated results say so and suggest a narrower request. Draft writes take `expected_revision` from `get_eval_set`.

## Content and safety

- Recorded prompts, outputs, tool arguments and raw attributes are omitted unless a tool is called with `include_content: true`. By default the server returns metadata (model, provider, usage, tool names, status, timing) and the names of recorded attributes. Content reads are recorded in the project's audit log.
- Names, generated titles, session keys, metadata and judge explanations come from your application and its end users. They are length-capped, and every result that carries them starts with a notice that they are data, not instructions; recorded content is wrapped in delimited blocks.
- Credential-shaped strings are redacted from results and from documentation queries before those leave Hue. The one exception is `add_api_key`, which returns the newly minted token once so it can be stored; later tools never return it.
- The key, or the project you approved at sign-in, is the tenant. Ids from another project, and `projectId` parameters on pasted links, resolve to `not_found`.
- Add `?read_only=true` to a key-based URL to hide and reject any write tool regardless of the key. With sign-in, choose **Read** at approval instead.
- Requests are limited to 1 MiB. Ten failed authentications for one key within a minute return `429` with `Retry-After: 60`, and for those 60 seconds the correct key is refused too. A busy server returns `503` with `Retry-After`.

## Troubleshooting

Several clients hide Hue's message behind a short status. The [curl check](#verify-the-connection) always shows it. `claude mcp get hue` (Claude Code), `opencode mcp debug hue` (OpenCode), **Show Output** (VS Code) and Claude Desktop's `mcp-server-hue.log` show it for most failures. Codex, Cursor and Gemini CLI report every `401` as a request to sign in. When you use a key, don't follow those prompts: find Hue's reason and fix the key.

| Symptom | Cause | Fix |
| --- | --- | --- |
| A Hue sign-in page opens, or the client shows **Needs authentication**, `Authentication required`, `requires_authentication` (Cursor), `The hue MCP server is not logged in` (Codex) or `OAuth not authenticated` (Gemini CLI), although you configured a key | Hue refused the key. Usually `HUE_MCP_KEY` is unset or empty where the client started, the header lacks `Bearer ` or repeats it, the key is in another header such as `x-api-key`, or the key is wrong or revoked. Also check that the saved configuration still holds the `${HUE_MCP_KEY}` reference rather than `Bearer` or the key (a CLI `--header` in double quotes), that no other `hue` entry without the header overrides it (Claude Code), and that Codex was added with `--bearer-token-env-var` | Run the curl check and match its message to the rows below. Export `HUE_MCP_KEY` in the shell that starts the client, restart the client, and send exactly `Authorization: Bearer <key>`. Don't finish a sign-in that opened because of a failing key: it fails too. |
| `Malformed initial access token Authorization header` (Cursor, OpenCode) or `Dynamic Client Registration rejected (HTTP 401) … Invalid initial access token` (Claude Desktop's `mcp-server-hue.log`) | The client tried to sign in and sent your failing key header along: the variable is unset or empty or already holds `Bearer `, or the key is wrong, a placeholder or an unexpanded `${…}` reference | Fix the key as in the row above, then restart the client. In Claude Desktop, `AUTH_HEADER` holds `Bearer ` and the key itself. Or remove the header and sign in. |
| Codex reports `Environment variable HUE_MCP_KEY for MCP server 'hue' is not set` or `… is empty` | The variable is missing, empty or set without `export` in the shell that started Codex | Export the key in that shell and restart Codex. |
| `401` `The bearer token is not a Hue credential` | The client sent something other than a key: the reference itself, such as `${HUE_MCP_KEY}`, because the variable was unset or the syntax is not the client's, or a value with extra characters such as surrounding quotes | Set the variable to the key alone before starting the client, and use the client's syntax: `${HUE_MCP_KEY}` for Claude Code and Gemini CLI, `${env:HUE_MCP_KEY}` for Cursor and Windsurf, `{env:HUE_MCP_KEY}` for OpenCode. Codex needs `bearer_token_env_var` and does not expand `${…}` in `http_headers`. Claude Desktop expands no shell variables, so `AUTH_HEADER` holds the key. |
| `401` `A valid project service key is required` | The key is wrong, truncated, revoked or expired | Copy the key again from your secret manager, or create a new one in **Settings → Integrations & API keys**. |
| `403` `This key cannot read project data` | The key is **Tracing only** or a legacy **Tracing and evaluations** or **Source capture (legacy)** key | Create a **Read** or **Read and write** key and set it as `HUE_MCP_KEY`, or, for Claude Desktop, put it in `AUTH_HEADER` after `Bearer `. Or [sign in with Hue](#sign-in-with-hue-instead-of-a-key). OpenCode shows this as **needs authentication**. |
| `Unexpected content type: text/html`, HTTP `404` or `MCP endpoint not found` | Wrong URL: the host root, `/api` without `/mcp`, or `/mcp` on `app.hue.run` | Use `https://mcp.hue.run/mcp` exactly. A trailing slash is fine. |
| `429` `Too many failed authentications for this key`, or `Too many requests. Please try again later.` while a client tries to sign in | Ten failed attempts with this key within a minute, often from another client with an old or truncated copy, or repeated sign-in attempts from a client whose key header keeps failing | Fix or stop that client, then wait a minute. Until then the correct key is refused too. |
| `503` with `Retry-After: 1` | The server is momentarily busy | Retry after a second. |
| Codex reports `invalid HTTP header`, or OpenCode says its configuration is not valid JSON | The stored key ends with a newline | Store the key without a trailing newline. OpenCode's error prints the key, so clear it from your terminal. |
| Cursor shows `not loaded (needs approval)` or `has not been approved` | Cursor has not approved the server, or `HUE_MCP_KEY` changed or became unset since you approved it | Check that `HUE_MCP_KEY` is exported and holds the key you intend, then turn on **hue** in Cursor's MCP settings, or run `cursor-agent mcp enable hue`. Cursor asks again after every change. |
| Gemini CLI shows **Disconnected** or **Disabled** | The key is not in the environment that started `gemini`, the folder is not trusted, or Hue refused the key | Export `HUE_MCP_KEY` before starting `gemini`, trust the folder with `/permissions`, and run the curl check for Hue's message. |
| A client you connected by signing in shows **Needs authentication** or `The hue MCP server is not logged in` | The approval ended: 30 days passed, someone disconnected it in **Settings → Connected apps**, you reset your password or signed out everywhere, or you left the organization or the project was archived | Sign in again: `/mcp` → **Authenticate** in Claude Code, `codex mcp login hue`, or `cursor-agent mcp login hue`. |
| A tool call fails as an unknown tool | Write tools are hidden for **Read** access and for a URL with `?read_only=true`; [retired tool names](#retired-tool-names) are no longer served | Use a **Read and write** key without `?read_only=true`, approve **Read and write** at sign-in, or call the current tool name. |

The server accepts `POST` only. A `GET` with no `Authorization` header, or with a value that is not a Hue key or token, gets `401` with the sign-in challenge. A `GET` that carries any Hue key or token gets `405` with `Allow: POST`; the key is not checked. A request carrying `Mcp-Session-Id` gets `404`, because the server keeps no sessions. MCP clients handle these answers themselves. See [troubleshooting](/guides/troubleshooting#the-mcp-server-rejects-the-agent) for tracing problems that are not specific to MCP.

## Release boundaries

Use the tools returned by your connection's `tools/list`. A tool described in a development branch is not available until its platform release is deployed; an unknown tool is not evidence that the client should broaden its permissions. Case conversion, review and publication are supported through the tools above. Billing and plan changes remain in Settings.

The Hue project-data MCP server is a hosted [Model Context Protocol](https://modelcontextprotocol.io) server at `https://mcp.hue.run/mcp`. There is nothing to install. Browser sign-in reaches the active projects in one organization, or can be [pinned to one](#pin-a-connection-to-one-project); a project key reaches its project. **Read** access searches and inspects project data, such as traces, evaluations and cases, and **Read and write** access also changes it. Billing and plan changes stay in Settings. `https://docs.hue.run/mcp` is a separate documentation-only server and cannot read your project.

A connection lists Hue's production reads, and `search_hue_tools`, which finds every other tool the connection can call, such as evaluations, cases and writes. Clients that search their own tool lists add `?toolsets=all` to the URL to list every tool directly. See [choose toolsets](#choose-toolsets).

## Quick start

1. Choose your client below and add the server URL it shows: `https://mcp.hue.run/mcp`, with `?toolsets=all` for a client that searches its own tools. For **sign-in with Hue**, leave out API keys and custom headers.
2. When the client opens Hue, sign in with your verified account. The consent page names the organization; check it and choose **Allow**. The connection can read and write every active project in that organization, within your role.
3. Refresh the client's MCP status or start a new session, then [verify the connection](#verify-the-connection) by reading a trace through the agent.

Use a [project key](#connect-with-a-project-key) instead for a client that can't sign in, such as Cursor or GitHub Copilot's cloud agent; for a run without a browser, such as CI or `claude -p`; for read-only access; or for access that must outlast a sign-in's 30 days. Then follow your client's key instructions below. A **Tracing only** key cannot connect to this MCP server.

<Visibility for="agents">
  **If you are a coding agent connecting with sign-in:** add the server as `hue` at the URL the user gave you, using your client's tab below, with no API key, token or headers. In Claude Code, keep `--scope user` so it works in every project. In Codex, `codex mcp add` opens the sign-in in the browser at once and waits for the user to approve it, so ask the user to run it in their own terminal, and to run `codex mcp login hue` once only if that sign-in did not finish. Ask the user to finish sign-in with the client's authentication action, and to start a new session if the Hue tools don't appear, then call `list_projects` to verify. If the client can't sign in, follow [connect with a project key](#connect-with-a-project-key) and let the user store the key.
</Visibility>

## Connect your client

Start with **Any MCP client** for the connection settings, or choose your client for exact commands.

      ```json .mcp.json
          "hue": {
            "type": "http",

              "Authorization": "Bearer ${HUE_MCP_KEY}"
            }
          }
        }
      }
      ```

      <Accordion title="If the Claude Code check fails">

If the `Headers` line shows only `Bearer` or a key, run `claude mcp remove hue -s <scope>` with the scope it reports, add the server again with single quotes, and rotate a key that was stored or printed. Placed before the server name, `--header` swallows the name and URL, and Claude Code reports `error: missing required argument 'name'`. `claude mcp list` warns `Missing environment variables: HUE_MCP_KEY` when the variable is unset.

        Claude Code keeps one `hue` entry per scope, and a local entry overrides project and user entries. To switch between a key and [sign-in](#sign-in-with-hue), run `claude mcp remove hue -s <scope>` with the scope `claude mcp get hue` reports, then add the other form. After you switch from sign-in to a key, new sessions can skip `hue` for about 15 minutes; run `/mcp` in a new session to confirm its tools are listed.

## Sign in with Hue

Sign-in uses OAuth and requires no project key. Your account must be verified and an actual member of the organization; any member can approve a connection, without an owner or admin role. If you were invited, accept the invitation in Hue first, then connect again. Only active projects appear. Administrative visibility without membership does not grant access to a connected app.

The consent page shows the app's name, the domain it returns to and the account you signed in with. It states that the app can read and write all projects in the organization it names; there is no organization, project or access-level choice. Hue uses the organization active in your Hue session, or your only organization. If you belong to several and the page asks you to switch, open Hue, switch to the organization you want and refresh the page. Check the account and organization before you choose **Allow**. An organization connection lists its active projects with `list_projects`, including projects created later; you can [pin its URL to one project](#pin-a-connection-to-one-project) when the agent should not choose among them.

Leave out the `Authorization` header and any bearer-token environment-variable setting when signing in. An old key entry can suppress sign-in or carry a failing header into authorization. Replace it using the instructions in your [client's tab](#connect-your-client).

<Accordion title="Access, expiry and disconnecting">
  - A sign-in connection always has **Read and write** access: write tools are available within your current organization role, and `add_api_key` is never available. Hue offers no read-only sign-in: `?read_only=true` on the URL hides write tools only while the URL carries it. For access that stays read-only, use a **Read** [key](#connect-with-a-project-key). A connection approved before sign-in covered whole organizations keeps its one project and access level until it expires.
  - The client receives access tokens that last 10 minutes and refreshes them automatically. Your approval lasts 30 days from when you connect; refreshing never extends it, so sign in again after that.
  - The connection acts for you. Writes are attributed to you, and owner- or admin-only tools check your current role: revoking keys, changing project settings or trace checks, archiving eval sets and evaluators, registering managed targets and publishing the intent taxonomy. A connected app can never create project keys with `add_api_key`.
  - Sign-in covers the MCP server only. Sending traces, `hue eval`, local agents and the REST API still need a project key as `HUE_API_KEY`.
  - **Settings → Connected apps** lists your connections and disconnects them; owners and admins see and disconnect everyone's in the organization. Resetting your password or signing out everywhere disconnects every app you approved, and removal from the organization ends the connection too. An archived project stops appearing to that connection.
</Accordion>

## Pin a connection to one project

Add `?project=<id-or-slug>` to the MCP URL to narrow a key or sign-in connection to one project it
already reaches. Combine it with a tool selection like this; keep the quotes because `&` has a
meaning in the shell:

```sh
claude mcp add --transport http --scope user hue-support-agent \
  'https://mcp.hue.run/mcp?project=support-agent&toolsets=all'
```

Name the server `hue-<slug>` so the pinned connection can sit beside an organization-wide `hue`
connection. For Codex TOML, the equivalent header form keeps the URL bare:

```toml
[mcp_servers.hue-support-agent]
url = "https://mcp.hue.run/mcp"
http_headers = { "X-Hue-MCP-Toolsets" = "all", "X-Hue-MCP-Project" = "support-agent" }
supports_parallel_tool_calls = true
```

`hue mcp install --client <client> --project support-agent` adds or replaces the query parameter,
keeps the toolset selection and uses the coexisting server name for you.

A pinned connection publishes no `project_id` argument. Its tools act on the pinned project, and
`list_projects` returns only that project with `connection.pinned: true`. Do not pass a stray
`project_id`: Hue rejects it even when it names the pinned project. The query and
`X-Hue-MCP-Project` header may be used together only when they name the same project. An empty pin
returns HTTP `400`. An unknown, archived or unreachable project returns HTTP `404` before an MCP
method runs; the credential is still valid, so signing in again does not fix it. Change the pin or
remove it.

## Connect with a project key

1. An owner or admin creates a **Read** key, or a **Read and write** key if the agent should change project data, in **Settings → Integrations & API keys**. Save the key in your secret manager; it is shown once. On a production server, keep it separate from the application's **Tracing only** `HUE_API_KEY`; on a development machine, the one **Read and write** key from [`hue login`](/sdks/cli#store-your-key) serves both.
2. For clients that read `HUE_MCP_KEY`, export the key alone, without `Bearer `, from your secret manager into the shell that starts the client. If your client offers a secure credential prompt, use that instead.
3. Follow your [client's tab](#connect-your-client), restart it from that shell and approve **hue** if asked. Desktop apps started from the Dock or a launcher do not inherit a terminal's variables.

Never put the key in application code, shared configuration or a prompt. See [project keys](/guides/project-keys) for access and rotation.

<Visibility for="agents">
  **If you are a coding agent:** reference `HUE_MCP_KEY` and never ask the user to paste the key. Adding configuration alone does not prove that the client connected. If the current session cannot load the server, use the [key check](#verify-the-connection), then ask the user to restart and [verify through the client](#verify-the-connection). For sign-in, let the user complete browser consent; do not request passwords or tokens.
</Visibility>

### Let your coding agent configure the key

For a client that supports environment-variable references, paste this into your coding agent, started from a shell where `HUE_MCP_KEY` is exported. If your client uses a secure credential prompt, configure the key there instead.

```text Prompt wrap
Connect me to Hue MCP.

It is a remote MCP server (Streamable HTTP) at https://mcp.hue.run/mcp. Authenticate with a bearer token read from the HUE_MCP_KEY environment variable — reference the variable, do not write the key into a config file.

Register it under the name "hue" using whatever MCP configuration my client uses, then call get_project_context and tell me which Hue project it reached.
```

Most clients load a new server only when they start, and Claude Code and Cursor also ask you to approve it, so the agent usually can't call `get_project_context` in the session that added `hue`. Restart the client from the same shell, approve **hue** if asked, and ask again. If the agent asks you to paste the key, point it at `HUE_MCP_KEY` instead.

## Verify the connection

Ask the agent in the client you just connected:

```text
Use Hue MCP: call list_projects and confirm which project to inspect. Then call get_project_context and show its 5 most recent error traces with links. For an organization connection, pass the project's id or slug as project_id on each call after list_projects. For a pinned connection, confirm connection.pinned is true and do not pass project_id.
```

Then ask it to call `get_trace` for one of the returned trace IDs. If there are no error traces, ask `search_traces` for recent traces without an error filter. An empty result is not an authentication failure; use a project with a known test trace to verify the full read path.

A successful check names the intended project and returns that project's trace through the MCP tool calls. A saved configuration or a **Connected** status alone does not establish that those calls work.

`get_project_context` returns the project the connection reaches and what the credential can do. `can_write` is `true` when write tools are available; `read_only` reports only the URL's `read_only` flag or the `X-Hue-MCP-Read-Only` header, so a **Read** key shows `read_only: false` together with `can_write: false`, and `write_preset` names the access that writing needs, not the access you have. If it reports a different project than you expected, the key was created in another project; on an organization connection, pass the intended project's id or slug from `list_projects` as `project_id`.

To check a key without an MCP client, send one tool call from a shell where `HUE_MCP_KEY` is exported. This is the check to use when a client shows only a short status, and the non-interactive check for a coding agent. It proves the key, not the client's configuration:

```sh
printf 'Authorization: Bearer %s\n' "$HUE_MCP_KEY" | \
curl -sS -w '\nHTTP %{http_code}\n' -X POST https://mcp.hue.run/mcp \
  -H @- \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"get_project_context","arguments":{}}}'
```

The shell's `printf` builtin sends the header through standard input, keeping the expanded key out of curl's process arguments. `HTTP 200` with an `event: message` response that names your project means the key works. `401` means the key is missing, wrong, revoked or expired, and `403` `This key cannot read project data` means it is not a **Read** or **Read and write** key; the response body explains the refusal, and the [troubleshooting](#troubleshooting) table lists the other statuses. The server needs both `Accept` types and answers `406` without them. It is stateless, so no session or `initialize` call is needed first.

## Troubleshooting

For key-based connections, the [curl check](#verify-the-connection) shows Hue's response when the client displays only a short status. Some clients treat any `401` as a request to sign in; fix or remove a failing key header before starting OAuth. For sign-in connections, use the client's authentication action and the sign-in rows below.

| Symptom | Cause | Fix |
| --- | --- | --- |
| The consent page names the wrong organization, asks you to switch organization, or says you're not a verified member | You belong to several organizations and another one is active in Hue, or the signed-in account is unverified, has not accepted its organization invitation, or is not a member | Open Hue, switch to the organization you want and refresh the consent page. Otherwise check the account shown on the page, verify your email and accept your invitation in Hue, then reconnect. Ask an organization owner or admin to check your membership. Staff or administrative visibility alone is not membership. |
| The client reports missing OAuth metadata | The URL is wrong, a saved entry still targets an old endpoint, or discovery failed | Use `https://mcp.hue.run/mcp` without a custom authorization header, refresh the client's configuration and retry. If it persists, report the client/version and error text without tokens. |
| Consent succeeds but no Hue tools appear | The running agent session has not loaded the new connection | Refresh MCP status and start a new session, then run the verification above. In Conductor, check the configuration for the selected agent. |
| A Hue sign-in page opens, or the client shows **Needs authentication**, `Authentication required`, `requires_authentication` (Cursor), `The hue MCP server is not logged in` (Codex), although you configured a key | Hue refused the key. Usually `HUE_MCP_KEY` is unset or empty where the client started, the header lacks `Bearer ` or repeats it, the key is in another header such as `x-api-key`, or the key is wrong or revoked. Also check that the saved configuration still holds the `${HUE_MCP_KEY}` reference rather than `Bearer` or the key (a CLI `--header` in double quotes), that no other `hue` entry without the header overrides it (Claude Code), and that Codex was added with `--bearer-token-env-var` | Run the curl check and match its message to the rows below. Export `HUE_MCP_KEY` in the shell that starts the client, restart the client, and send exactly `Authorization: Bearer <key>`. Don't finish a sign-in that opened because of a failing key: it fails too. |
| `Malformed initial access token Authorization header` or `Dynamic Client Registration rejected (HTTP 401) … Invalid initial access token` | The client tried to sign in and sent your failing key header along: the variable is unset or empty or already holds `Bearer `, or the key is wrong, a placeholder or an unexpanded `${…}` reference | Fix the key as in the row above, then restart the client. Or remove the header and sign in. |
| Codex reports `Environment variable HUE_MCP_KEY for MCP server 'hue' is not set` or `… is empty` | The variable is missing, empty or set without `export` in the shell that started Codex | Export the key in that shell and restart Codex. |
| `401` `The bearer token is not a Hue credential` | The client sent something other than a key: the reference itself, such as `${HUE_MCP_KEY}`, because the variable was unset or the syntax is not the client's, or a value with extra characters such as surrounding quotes | Set the variable to the key alone before starting the client, and use the client's syntax: `${HUE_MCP_KEY}` for Claude Code and `${env:HUE_MCP_KEY}` for Cursor. For other clients, follow their environment-variable or secret-storage syntax. Codex needs `bearer_token_env_var` and does not expand `${…}` in `http_headers`. |
| `401` `A valid project service key is required` | The key is wrong, truncated, revoked or expired | Copy the key again from your secret manager, or create a new one in **Settings → Integrations & API keys**. |
| `403` `This key cannot read project data` | The key is **Tracing only** or a legacy **Tracing and evaluations** or **Source capture (legacy)** key | Create a **Read** or **Read and write** key and configure it in your client. Or [sign in with Hue](#sign-in-with-hue). |
| `403` `Origin is not allowed.` | A browser-based client or web page called the server from an origin Hue does not accept. The key or sign-in is not the problem | Connect from a CLI or desktop client, a hosted connector described in [connect your client](#connect-your-client), or a local tool served from `localhost`, such as MCP Inspector. |
| `413` `MCP request exceeds 1 MiB` | The request body is larger than 1 MiB, usually a large batch of cases or a long JSON argument | Split the call, for example into several `add_eval_set_cases` calls of at most 25 cases. |
| `415` `Content-Type must be application/json` | A hand-written HTTP client sent another content type | Send `Content-Type: application/json` and the `Accept` header the [curl check](#verify-the-connection) shows. MCP clients set both. |
| `400` says the project pin is empty or the query and header name different projects | The URL has an empty or conflicting `project` selection | Name one project id or slug in `?project=`, make `X-Hue-MCP-Project` match it, or remove the pin. |
| `404` says the project this MCP URL pins is not reachable | The project is unknown, archived, outside the credential's organization or different from the project key's project | Change the pin to an active project this credential reaches, or remove it. Signing in again does not fix this response. |
| `Unexpected content type: text/html`, HTTP `404` or `MCP endpoint not found` | Wrong URL: the host root, `/api` without `/mcp`, or `/mcp` on `app.hue.run` | Use `https://mcp.hue.run/mcp` exactly. A trailing slash is fine. |
| `429` `Too many failed authentications for this key`, or `Too many requests. Please try again later.` while a client tries to sign in | Ten failed attempts with this key within a minute, often from another client with an old or truncated copy, or repeated sign-in attempts from a client whose key header keeps failing | Fix or stop that client, then wait a minute. Until then the correct key is refused too. |
| `503` with `Retry-After: 1` | The server is momentarily busy | Retry after a second. |
| The client reports `invalid HTTP header` | The stored key ends with a newline | Store the key without a trailing newline. |
| Cursor shows `not loaded (needs approval)` or `has not been approved` | Cursor has not approved the server, or `HUE_MCP_KEY` changed or became unset since you approved it | Check that `HUE_MCP_KEY` is exported and holds the key you intend, then turn on **hue** in Cursor's MCP settings, or run `cursor-agent mcp enable hue`. Cursor asks again after every change. |
| A client you connected by signing in shows **Needs authentication** or `The hue MCP server is not logged in` | The approval ended: 30 days passed, someone disconnected it in **Settings → Connected apps**, you reset your password or signed out everywhere, or you left the organization | Use your client’s authentication action to sign in again: `/mcp` → **Authenticate** in Claude Code or `codex mcp login hue` in Codex. For Cursor, use the project-key instructions in its tab until native sign-in is supported. |
| A tool call fails as an unknown tool, or with `forbidden_capability: <tool> is not listed on this connection` | The connection does not list the tool: by default it lists the production reads. A tool your access allows but the connection's toolsets leave out answers `forbidden_capability`, with a hint that names its executor. Write tools are hidden entirely for **Read** access and for a URL with `?read_only=true`, so a call to one fails as an unknown tool, and a tool described in a development branch is not available until its platform release is deployed | Find the tool with `search_hue_tools` and call it through the executor its `call` field names, or add `?toolsets=<group>` or `?toolsets=all` to the server URL and reconnect. For a write tool, use a **Read and write** key or a sign-in connection, without `?read_only=true`. An unknown tool is not evidence that the client should broaden its permissions. |

See [troubleshooting](/guides/troubleshooting#the-mcp-server-rejects-the-agent) for tracing problems that are not specific to MCP.

<Accordion title="Endpoints and protocol details">
  The project-data server is available only at `https://mcp.hue.run/mcp`. The `search_hue_docs` tool delegates documentation searches to the Mintlify-hosted documentation endpoint without changing the project-data server's authentication boundary.

  The server is stateless and accepts clients that start with `initialize` (MCP revisions up to 2025-11-25) as well as clients on the stateless 2026-07-28 revision, so clients need no extra flags. It accepts `POST` only. A `GET` or `DELETE` without a Hue credential in `Authorization` gets the `401` a `POST` would: no header, an empty `Bearer ` that an unset variable leaves, an unexpanded `${HUE_MCP_KEY}` or any other token. One carrying a well-formed Hue key or sign-in token gets `405` with `Allow: POST`, without the credential being verified, so use the POST key check above to diagnose a failing key. A request carrying `Mcp-Session-Id` gets `404`, because the server keeps no sessions. A request from a browser origin Hue does not accept gets `403`, a body over 1 MiB `413`, a body that is not `application/json` `415`, and a JSON-RPC batch (a JSON array of messages) `400` with error `-32600` before any of its messages runs; send one message per POST. MCP clients handle these answers themselves.
</Accordion>

## What you can do

A project key reaches one project. A sign-in connection that covers an organization lists its projects with `list_projects`, and every other project tool then takes the chosen project's id or slug as `project_id`. A connection pinned by URL or header instead has a single-project shape: its schemas omit `project_id`, and `list_projects` returns its one project with `connection.pinned: true`. Write tools need **Read and write** without `?read_only=true`. Ask before any write, and never auto-approve one; the [security model](#security-model) explains why.

A default connection lists the production reads; the other tools below are one [`search_hue_tools`](#choose-toolsets) call away, or listed directly with `?toolsets=all`. The [tool reference](/agents/mcp-tools) lists every tool by toolset with the access and role it needs.

Each workflow below starts with prompts you can give your coding agent as written; replace the placeholders in angle brackets. For production questions (what needs attention, which tools fail, which task types or steps are slow, time to first reply, release regressions, one user's traces), [Investigate production](/agents/investigate-production) gives more prompts, the tool sequences, the fields, the finding and attention states, and the limits and error codes.

Hue-owned argument and output names are recursively `snake_case`. Recorded span attributes and app data inside `content_json` keep the application's own keys; `upload_headers` preserves literal HTTP header names. JSON arguments that round-trip a returned trace-check definition, calibration or judge bar use those returned `snake_case` keys and reject camelCase. Time windows accept ISO-8601 or relative values such as `15m`, `24h` or `7d` (up to 90 days). Results are paginated with opaque cursors and bounded by `max_chars`; paged lists, including `get_trace_check_results` and `list_intent_traces`, return `next_cursor`. A paged list past `max_chars` returns the rows that fit, with `omitted_count` and a cursor that continues after the last row; any other result that has to be shortened says `truncated: true` with a hint. ### Product vocabulary

MCP ids are named after the object they identify. Evaluation tools use `eval_set_id`, `eval_set_version_id`, `from_eval_set_version_id` and `eval_set_case_id`; `evaluator_id`, `evaluator_version_id` and `evaluator_version_ids`; `run_id` and `baseline_run_id`; and `scoring_run_id` and `scoring_item_id`. Run dispatches use `managed_run_id` and `local_run_id`. Reviewed cases use `case_id`, environment versions use `environment_version_id`, and trace-check versions use `trace_check_version_id` or `active_trace_check_version_id`.

Evaluation list results are named `eval_sets`, `evaluators`, `runs`, `scoring_runs` and `cases`. Single-object results use the matching singular name, such as `eval_set`, `evaluator`, `run`, `scoring_run`, `case`, `managed_run` or `local_run`. A row's own identifier stays `id`; foreign identifiers spell out their object, such as `eval_set_version_id` on a run or `evaluator_version_id` on a scoring result.

## Choose toolsets

Without a selection, a connection lists the `observe` toolset, the production reads: `list_projects`, `get_project_context`, `search_traces`, `get_trace`, `get_span`, `list_sessions`, `verify_trace`, `get_span_content`, `search_spans`, `aggregate`, `get_intent_summary`, `list_intent_traces`, `get_request_answer`, `search_hue_docs` and `load_hue_guide`. Beside them it lists three catalog tools that reach every other tool the connection's access allows, so a short list loses nothing:

- `search_hue_tools` finds tools by keywords, such as `eval set`, or by `toolset`, 10 per page. Each result has the tool's `name`, `toolset`, `summary`, `access`, `input_schema`, `annotations` and `call`: the tool's own name when the connection lists it, otherwise the executor to call it through.
- `execute_hue_tool` calls a read tool by `name` with its `arguments` and returns exactly what calling it directly returns.
- `execute_hue_write_tool` calls a write tool the same way. It is listed only with write access and without `?read_only=true`. Ask the user before calling it.

That is 18 tools with write access, or 17 tools with **Read** access. An executor call goes through the same access checks, project selection, audit log and content gating as a direct call. For example, to list an organization project's eval sets on a default connection, call `list_projects`, then `search_hue_tools` with `query: "eval set"`, then `execute_hue_tool` with `{"name": "list_eval_sets", "arguments": {"project_id": "<id>"}}`.

## Security model

The agent you connect acts with your credential, and everything your application recorded reaches it as data from outside Hue. These rules follow from that; [permissions](/agents/mcp-tools#permissions) lists what each credential and role can do.

### Treat recorded data as untrusted

- Names, generated titles, session keys, metadata, judge explanations and recorded prompts, outputs and tool results come from your application and its end users. Any of them can carry text written to steer an agent, a prompt injection. They are length-capped, and every result that carries them starts with a notice that they are data, not instructions, repeats it as `structuredContent.untrusted_notice` and sets `_meta["hue.run/untrusted"]` to `true`; recorded content is wrapped in delimited blocks.
- An instruction found in that data is a quote, never a request from you. Don't let the agent act on one, and review recorded text before it goes into a write's arguments or a documentation search.

### Content is opt-in and audited

- Recorded prompts, outputs, tool arguments and raw attributes are omitted unless a tool is called with `include_content: true`, or read with `get_span_content`. By default the server returns metadata (model, provider, usage, tool names, status, timing) and the names of recorded attributes.
- Hue records each content read in the project's audit log with the credential and the objects read, never the content; for a sign-in connection the member who approved it is the actor. Ask for content only when the question needs it and your capture policy allows it. `content_not_captured` means the application recorded that trace without content.

### Approve every write

- Write tools exist only with **Read and write** access and without `?read_only=true`. Every write tool carries `readOnlyHint: false`, whatever its name, and every read tool `readOnlyHint: true`.
- Ask before any write, naming the project and the object it changes. Never auto-approve a write, in particular `add_*`, `delete_*`, `archive_*`, `revoke_api_key`, `cancel_managed_run` or `execute_hue_write_tool`, which can call any write. If your client approves tools automatically, allow read tools only.
- `destructiveHint: true` marks every `update_*`, `set_*`, `activate_*`, `deactivate_*`, `archive_*`, `cancel_*`, `revoke_*` and `delete_*` tool; `freeze_eval_set_version`, `finish_run`, `complete_run_case`, `start_run_case` (a retry supersedes the started attempt), `publish_case_conversion` and `save_intent_taxonomy`, which change or seal something that exists; and `execute_hue_write_tool`. `search_hue_docs` and `launch_managed_run` carry `openWorldHint: true` because they reach outside Hue, and every `set_*` tool carries `idempotentHint: true`. Annotations are client hints, not permission to write without confirmation.
- Writes to eval set drafts, trace checks and case conversions take the `expected_revision` the last read returned, so a write never overwrites a change it did not see, and new runs, launches and case drafts take an `idempotency_key`, so a retried call with the same body returns the original. A write whose `idempotentHint` is `false` that fails with `timeout` or `unavailable` may still have completed, so Hue reports that failure as not retryable, with a hint to read the write's state before you try again.

### Tenant and credential boundaries

- The key's project, or the project a sign-in connection selects with `project_id` or its pin, is the tenant. Ids from another project, and `projectId` parameters on pasted links, resolve to `not_found`.
- A sign-in connection acts for the member who approved it, within that member's current role, and can never create project keys. A key acts for its project; owner- and admin-only tools check its creator's current role.
- Add `?read_only=true` to the URL, or send `X-Hue-MCP-Read-Only: true` from a client whose configuration cannot carry a query string, to hide and reject any write tool, whatever the credential allows, sign-in included. Any value other than `false`, `0`, `no`, `off` or empty counts as read-only, and a second value cannot turn it off. It lasts only while the request carries it; the credential keeps its access. For read-only access the credential itself enforces, use a **Read** key.
- Credential-shaped strings are redacted from results and from documentation queries before those leave Hue. The one exception is `add_api_key`, which returns the newly minted token once so it can be stored; later tools never return it. Keep keys in a secret store and out of URLs, shared configuration and prompts.
- Requests are limited to 1 MiB. Ten failed authentications for one key within a minute return `429` with `Retry-After: 60`, and for those 60 seconds the correct key is refused too. A busy server returns `503` with `Retry-After`. The [limits](/agents/investigate-production#limits-and-errors) cover result sizes, pages and query time.
